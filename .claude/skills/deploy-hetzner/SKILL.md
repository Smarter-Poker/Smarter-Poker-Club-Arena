# Club Arena engine delivery

Read root `AGENTS.md`, `PUBLISHING.md` and `docs/agent-policy/OPERATING-LAW.md` first. These are the current authority for submission, publication, recovery and access. This skill does not assign another development phase or override a required check.

## Classify and prepare promptly

Only engine activation requires the maintenance owner's certified opportunity. Push checked source, complete required checks and protected merge, and build/stage the immutable image throughout the hour. An ordinary client change using an existing engine API publishes and verifies immediately through `publish-club-arena.yml`; it does not wait for an engine SHA or `:55`.

The protected engine route is:

```
protected main -> stage-engine-release.yml (select exact runtime revision)
               -> auto-deploy-hetzner.yml (qualify, build and stage promptly)
               -> existing host transaction (certified activation, proof, seal)
```

Read the existing stage, dispatch and owning transaction results before acting. A merge can start publication but does not prove that publication completed. Reattach to an existing operation; do not duplicate its dispatch or restart a target already healthy and serving. Inspect the maintained workflow's actual accepted event and exact revision selection if a demonstrated missing dispatch needs repair. Use configured authenticated GitHub tools and ordinary protection; never infer missing access from one interface failure.

## Access and production safeguards

Necessary credential or configuration repair within the assigned delivery needs no additional human approval. Inspect supported access and secret metadata early. Preserve the intended service identity, least privilege and configured secret store. Never read workstation `.env` values, print key material, substitute another App identity or invent a credential fallback. Higher-priority tool handoff requirements and actual authentication constraints remain; finish independent work while a genuinely unavailable input is resolved.

Production authority comes from the existing GitHub workflow and its configured Hetzner credentials. Do not treat a dated host address or workstation key path as current access proof. No raw SSH deployment, hand-built container, alternative publisher, local runner or recurring release mechanism is authorized.

`server/scripts/engine-up.sh` remains the single container start path under the existing release lock. Preserve its release labels, health configuration, logging bounds and immutable image/seal identity. Never replace the container, repoint its image tag, prune retained rollback images, reduce the proof reserve or extend a live freeze by hand.

## Recovery and completion

Inspect a failed build, precheck, staging or proof result immediately and correct its cause. Do not park a ready correction until the next hour. Unknown side effects retain their owning operation identity; a timeout does not authorize a blind retry. The bounded additional recovery opportunity requires the actual installed maintenance/database/release capability and its certified admission. Source documentation alone cannot provide it. Until installation is verified, preserve the serving runtime's real guards and prove the first transition safely.

Completion requires the actual owning release result and sealed receipt, exact expected component identity at `https://engine.smarter.poker/health`, healthy stable runtime, and the applicable table/hand/connected behavior checks. Record the selected runtime SHA separately from later documentation-only main commits. Failed or missing proof remains unfinished even when the build or workflow is green.

Existing observation-only reports may provide evidence. Do not depend on an observer, scheduler, another chat or future manual approval to advance, retry or certify the assigned release. Continue personally through all executable checks and publication, preserving actual provider serialization and financial safeguards.
