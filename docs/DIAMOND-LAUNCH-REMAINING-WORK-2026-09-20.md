### The migration record, read properly

The programme's verification standard says a migration file is not an applied migration, so I checked. The naive check is misleading and I want to record why, because it will mislead the next reader too.

`supabase_migrations.schema_migrations` holds 4,766 rows. `supabase/migrations/` on `main` holds 3,215 files across 2,728 distinct version prefixes. Comparing the two **by version** suggests 467 files since 2026-09-01 are not installed. That number is wrong. `apply_migration` records the version of the moment it ran, not the version in the filename, so the same migration routinely appears on `main` as `20260912004100_a_diamond_seat_tops_up...` and in the history as version `20260912004350` under the same name. The reliable key is the **name**.

Compared by name, since 2026-09-08, exactly **21** migration files on `main` have no matching name in the history. Of those:

- **Two are load-bearing and genuinely absent.** `20260918232558_mixed_f06_custody_transfer_retains_original_operations.sql` and `20260919024039_unresolved_f06_custody_retains_its_lease_evidence.sql`. I verified the absence at the object level, not just the record level: none of `fn_f06_admit_mixed_manager_custody`, `fn_f06_complete_mixed_manager_custody`, `fn_f06_find_mixed_manager_custody`, `fn_f06_mixed_custody_intent`, `fn_f06_prepare_mixed_manager_custody` appears in `pg_proc`. These are the engine-activation prerequisites.
- **Two are superseded, not missing.** `mtt_activate_unlimited_admission` and `mtt_activate_unlimited_with_original_funding` were both replaced by `mtt_activate_unlimited_with_satellite_entry_club`, which is installed.
- **Four are record-format noise.** `horse_profile_authority_is_server_only`, `horse_identity_triggers_use_canonical_profiles`, `one_club_shop_item_offers_all_throwables` and `an_arena_table_is_governed_by_the_diamond_boundary_not_a_clu` are all in the history, either with the version string duplicated into the name field or truncated at a different length than the filename.
- **The rest are chip-estate or renamed on apply**, for example `retire_the_six_stranded_half_chips_on_the_felt` against the installed `retire_the_stranded_half_chips_on_the_felt`.

Only one is Diamond-named and worth a second look: `20260908124528_diamond_engine_spend_report_is_private_by_construction.sql`, which creates `fn_ca_diamond_engine_spend_is_immutable` and its trigger. I did not check whether that trigger exists, and it is not on any launch path.

**The reverse direction is worse and is nobody's launch blocker.** 702 installed versions since 2026-09-01 have no file at that version on `main`, and one row's version is the literal string `manual`. Almost all of that is the same apply-time renumbering seen from the other side. It is a real bookkeeping defect, it is what open PRs #4960 and #4425 exist to fix, and it means `check-migrations-applied` can only ever be trusted about migrations a pull request itself changed. It does not block opening.

## 5. Risks and unknowns

**What I could not determine, and why.**

- **Whether the re-landed Phase 8 and 9 code behaves correctly.** I verified that `ab9e626376` is an ancestor of `main`, that the named boundary and manager files carry the Diamond arms, that the test files exist, and that all nine Phase 8 and Phase 9 migrations are installed. I did not run the test suite, and no funded Diamond tournament has ever completed. The Phase 8 exit gate is met in isolated certification only. Treat the ticks as "delivered and pinned", not "proven in production".
- **Whether the health watch will in fact resolve the 45 rows.** I read the migration and it puts the resolution where the filing is, but I cannot execute it. The runbook's abort condition, two full hourly ticks with `still_open` unchanged, is the right stop.
- **Whether `20260918232558` applies cleanly.** It creates functions, a `smarter_private` table and four triggers. I read what it declares, not whether every object it touches is in the state it expects.
- **Whether Phase 10 is closer to done than the checkboxes say.** Real readers are built and installed. I did not audit them line by line against the phase items, so I left every line unticked rather than claim credit I had not checked.
- **The full extent of the pre-September migration record drift.** I compared by name only from 2026-09-08 forward, which covers the whole Diamond programme. Earlier drift exists and I did not characterise it.

**Risks worth naming.**

- **The Diamond SQL acceptance suite has never run in CI.** This is the single largest unguarded surface. Eleven runners certifying custody, the transfer, the buy-in, the top-up, the straddle, run-it-twice, the bomb pot, the plain-cash rule, the accepted hand and a full controlled hand, none of them in a required check. PR #4951 fixes it and is currently red.
- **`check-migrations-applied` cannot be trusted as a whole-history gate.** With 702 installed versions having no file at that version and 21 named files with no record, the gate is only meaningful for migrations a pull request itself changes. Do not read a green CI run as "the repository and production agree".
- **The F06 permit pile grows with every engine restart and nothing can drain it.** 684 reserved permits across 463 tournaments, and `fn_f06_finish_hand` offers two outcomes, neither of which fits: `accepted` needs a `hand_atomic_commits` row that does not exist, `never_started` needs a `park_requested` operation almost none of them has. This is a platform defect owned by F06, not by this programme, and it is why the engine never hands over. It wants the third outcome described in `docs/changelog/2026-09-18-the-permit-nobody-can-resolve.md`.
