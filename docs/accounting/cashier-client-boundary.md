## Remaining qualification and implementation boundaries

- Separate browser tabs do not share the in-memory invocation sequence. A tab still resolving or hashing when another tab acknowledges may reserve after the shared key is removed. Same-operation server replay is protected by its UUID; universal cross-tab duplicate-intent prevention is not established by this client source. The server refuses a second hold while a pending request exists; the remaining interval is a delayed tab reserving after the first cashout becomes terminal. A reviewed cross-tab start/acknowledgement protocol remains open.
- The tests exercise local component/transport/operation boundaries only when admitted and executed. They cannot establish native SQL atomicity, real authentication/RLS, provider push delivery or a deployed receipt.
- Historical holds without new canonical event provenance and departed players without a verified refund wallet remain explicit server refusals. No historical adoption, membership recreation or invented funding is included.
- The canonical expiry worker admits only requests with recorded hold events. A private service-only inventory exposes unsupported historical holds for reconciliation; its processed count never certifies the whole queue. Actual expiry scheduling and historical disposition remain open.
- Club departure still contains its pre-existing separate hierarchy cleanup and treasury RPC. The changed cancellation step is receipt-bound; this does not certify the entire departure as one transaction.
- Browser agent sends, claim-backs, administrative removals, promo transfers, issuance and correction routes are outside this cashout v2 receipt contract. Existing source audit gaps remain open.
- The final DB bundle and compatible CA/WH readers require coordinated protected staging. The new client must not fall back to old successful-looking results; old writers are retired by the matching component. Activating only one side is not qualified.
- The World Hub request/approve/cancel route bridge uses each verified caller's original token and the same v2 authority. Its existing MFA, settlement and maker/checker gates remain required for new movement. Route-level platform or union permission does not replace the database's active club/downline authority. These changes require the matching final WH source and protected qualification.

An authenticated exact-operation receipt lookup allows the original actor to confirm a completed operation even if a current pre-payment gate has changed or is unavailable. It checks the full operation intent and existing canonical event, payment and delivery witnesses without creating financial or delivery records. It acquires database locks and therefore requires a normal transaction; it is not callable inside a PostgreSQL READ ONLY transaction. Only an explicit verified absent result permits the routes to continue through every new-payment gate. Errors, legacy witnesses, mismatches and corrupt receipts refuse. A found financial receipt does not certify an unchecked approval or audit trail, and a known failure recording that trail must not hide the already confirmed payment.

Required protected cases include late/silent invoice, message, notification and outbox failures; exact wallet/escrow/journal rollback; duplicate operations and conflicting decisions; stale role/assignment and account transitions; current and historical holds; read failure and reload behavior; concurrent browser tabs; expiry caller/schedule ownership; and independent reconciliation of every committed event and delivery artifact. None of those production outcomes is inferred from source review.
