# Cashout client generation protocol — source candidate, UNRUN

This successor is based on reviewed CA `09b80f1765742ee94dc0016ef6cfa6aa2b77b7c8`. It changes client coordination and recovery only. The existing cashier v2 database transition remains the financial authority. No migration, payer, notification sender or provider-delivery claim is added. Tests, type checking, builds, native browser qualification and live behavior have not run for these bytes.

## Accepted intent and durable identity

Prepare the canonical account, club, player, action, target, amount and note while the form or row is idle. Disable submission until that preparation belongs to the current input and source revision. Capture the prepared start synchronously at the accepted gesture, before any await. Alias/hash delays cannot rebind an accepted start to a newer generation.

The cashout-only v2 history retains every generation, operation UUID, accepted start and acknowledgment. It uses the old cashout digest and WebLock name so an unresolved v1 UUID remains addressable. Migration saves and reads back full history before replacing the shared v1 slot with a marker. Conflicting or missing histories/pointers refuse. There is no TTL, pruning, automatic retry, fallback UUID or persistent personal/amount/note history. Storage quota exhaustion refuses new coordination.

A delayed G1 start remains G1 after another tab acknowledges G1 and a refreshed idle form completes G2. Terminal actions retain their exact UUID. A later request may prepare a new generation only after its prior acknowledgment is represented; an unacknowledged tab pointer still selects its original generation. Local acknowledgments coordinate operation identity and are never financial receipts.

## Recovery before new-payment checks

`recoverCashoutOperation(start)` admits the exact generation and calls existing `fn_cashout_operation_receipt_v2` through `CashoutService.lookupCashoutOperation`. It validates the complete actor/action/operation/club/amount/target/note envelope. Only literal, exact `found:false` plus `receipt:null` means absence. Errors, missing resolver, malformed/extra/mismatched fields, legacy witnesses and invalid receipt data refuse. A found receipt must be replayed and pass the existing strict canonical cashier receipt parser, including current request status.

A found result returns the actual DTO (hold) or verified terminal success; it bypasses new-payment checks and does not certify their current state. An absent result is bound to that opaque start. Only then may its caller perform the existing new-payment balance, settlement and confirmation checks and call `runCashoutOperation(start)`. The wrapper refuses dispatch without a completed lookup. A lookup is never automatically retried on the same start. A separate explicit gesture can check the same retained operation again. A concurrent commit after an absent lookup is still addressed by the original operation UUID; a failed later UI preflight requires another explicit check.

The modal and Cashier page offer **Check Or Request Cashout**, including when displayed balance is unavailable/insufficient. Exact absence still refuses a new hold under those conditions or a settlement lock. Existing server eligibility remains authoritative; no role or balance rules are copied into the wrapper.

High-value confirmation calls `confirmCashoutOperation(originalStart)` before its new-payment balance/lock gates. This explicit confirmation permits one further receipt observation on the already admitted hold generation and full intent. The earlier absence is revoked synchronously; a concurrent dispatch refuses until the new lookup establishes exact absence. Ordinary recovery and repeated confirmation calls share that new promise, including a failure. A found receipt is shown without payment even if another tab completed the hold while the dialog was open and the displayed balance or lock changed. Confirmation cannot begin after any execution starts and never creates another operation UUID.

## View lifecycle and own events

All six caller paths use the protocol: modal request/cancel, agent panel decision, agent dashboard decision, Cashier request (including the original high-value confirmation), and each exact pending cancellation during leaveClub. The leave flow remains a series of operations; it is not an atomic whole departure.

Pending-row reads started before acceptance retire old preparations. Ordinary queue/dashboard refresh initiation is deferred while accepted cashout actions are in flight and drained once afterward. This prevents actual service balance/cashout events or realtime notifications from retiring the row between canonical receipt validation and acknowledgment. Account, route, dialog and input fences remain immediate and sticky across ABA changes. A fresh current view can explicitly recover the same operation while an older view's transport remains pending. Old completion/finally cannot delete the newer coalesced submission or unlock its UI.

Displayed pending rows and their totals also retain their original account/view guard independently of the stricter action/read-generation guard. A render after an auth-epoch change hides the old rows while the new read is pending, including a batched A→B→A with the same final user ID. Ordinary same-scope refresh can keep its rows visible while actions remain unavailable. The Cashier confirmation display is likewise bound to its captured start.

The four outer caller wrappers use `useCashoutScopeKey`, which listens directly to `AUTH_STATE_CHANGED` and schedules a render even when the final user ID is unchanged. A changed sticky account/view token or availability remounts the local content with fresh busy and read refs. Repeated unavailable auth events keep one stable key. The listener subscribes before its initial refresh and unsubscribes on cleanup. This closes the old-scope deferred-reload/busy-state leak; remote work may still commit, and only the existing durable operation plus canonical lookup can establish its outcome after a fresh explicit gesture.

Agent panel, agent dashboard and modal cancellation retain an in-memory **Check Receipt** card when outcome verification fails. The opaque original retains its full canonical intent and generation, independently of later queue removal. Explicit receipt-only recapture requires the original account/view scope and a fresh current scope. It preserves the exact generation and cannot dispatch a payer even after authoritative absence. Unknown/absent stays unresolved; found is validated and acknowledged before the card is removed. No personal intent is written to persistent storage. Account/route retirement removes access immediately; reload recovery of a removed terminal row is not supplied by this in-view card.

Storage/WebLock rejection during acknowledgment returns false from the coordination helper and does not erase a verified financial result. Retained history/pointer lets a later explicit check reconcile the same operation. A WebLock that never settles is an unresolved liveness qualification boundary; no local timeout is represented as cancellation.

## Required protected qualification

Authored sources include real wrapper/storage/service tests; mounted modal and Cashier tests; leaveClub and agent-panel scope tests; and mounted agent panel, modal and dashboard tests using the actual MasterBus emitter, subscribers and debounce with actual wrapper/receipt parser. Provider RPC data and browser locks remain fixture boundaries, not database or native multipage proof. Existing receipt service, amount, scope and noncashout durable transfer regressions remain required too.

The admitted catalog must execute these exact final bytes and include:

- Native two-page WebLocks/localStorage/sessionStorage: G1 accepted then delayed admission; G1 acknowledged; G2 completed; late G1 still exact old UUID; same-generation concurrent starts; a reopened current view against an old pending response; no old finally deleting newer state.
- A late G1 acknowledgment while G2 remains admitted and unacknowledged must retain G2's exact live session pointer and history. The authored unit swaps a simulated tab session over shared history; native distinct browser pages remain required.
- Interrupted history initialization, marker replacement, activation, accepted-start and tab-pointer writes; interruption/readback refusal; old-client completion against markers; unknown conflicting legacy IDs; missing or replaced history; a legacy tab's UUID behind G2; no automatic advancement of unknown operations.
- Lost response with balance reduced to zero/unavailable and settlement changed; verified found avoids a payer; exact false retains each payment gate; unknown/malformed/old/wrong-actor/action/operation/target/amount/note receipts refuse; auth/input/route ABA during lookup/preflight/dispatch.
- Real notification/realtime listeners firing before service return and while acknowledgment waits; once-only trailing refresh; ordinary pre-acceptance read retirement; immediate account/route retirement.
- Previously visible panel/modal/dashboard/Cashier pending rows must disappear on a batched auth-epoch change while the new read remains unresolved. Actual bus tests cover the first three surfaces; the Cashier mounted case controls its account-epoch seam.
- Actual auth notification must wake outer wrappers without a caller rerender while an old action remains pending. New scoped reads/actions proceed independently; a late old completion cannot clear fresh busy state or invoke completion callbacks. The real service/bus mounted cases retain the same terminal operation UUID for the fresh explicit lookup/transition replay; native tab/server locking remains separate. Unavailable repeated events must not continually remount, and unmount must remove the listener.
- High-value dialog stays open while another tab finishes the same hold; explicit confirmation observes the original receipt under newly insufficient balance/lock. Concurrent run/recover while confirmation waits, unknown confirmation, repeated confirmation, account ABA and prior execution must never restore stale absence or mint another operation.
- Terminal row removal after unknown response; explicit same-operation receipt-only check; unknown remains unknown; found removes the card after proof; receipt-only starts cannot pay even with exact absence; original view/account retirement prevents recapture; no cross-reload identity reconstruction.
- Confirmed result preserved on acknowledgment failure for both transition and found-recovery paths; quota/readback errors refuse safely; unresolved native-lock liveness stays explicit.

Protected full application import/type/build and native client tests, matching applied CA33 resolver/transition/receipt authority, deployment provenance, notification/provider delivery, scheduler behavior and production financial reconciliation remain separate outstanding evidence. This source candidate cannot support a claim that the system is fully deployed, permanently infallible, or universally recoverable across reloads.
