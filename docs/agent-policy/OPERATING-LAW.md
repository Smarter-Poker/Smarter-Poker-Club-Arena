# Smarter Poker agent operating law

Policy version: 2.9 — September 17, 2026. This file owns continuity, delivery classification and recovery. Authorization/routes are in `OWNER-POLICY.md`; implementation requirements are in `HARDENING.md`. On the owner's Mac their canonical names are listed in `REFERENCE-INDEX.md`.

## 1. Maintain finite ownership

Keep scope, expected behavior, acceptance criteria, exclusions, owned checkout/branch/PR and actual operation owner in the existing task checkpoint. Supporting changes are in scope only when needed for the assigned behavior or a demonstrated blocker; record why. An unrelated discovery or spare time is not another assignment. A checkpoint records authority already granted; it cannot grant authority. A one-time exception ends at its stated limit.

The assigned agent owns source, required checks, protected merge, installation, publication and live verification. Inspect provider results directly. Another chat, unavailable helper or optional review is not a release gate and does not transfer ownership. Recover an unavailable helper's work and finish it yourself only after confirming actual handoff/no active competing writer. Preserve source and operation identity. This rule does not authorize delegation or unsolicited messages.

One writer owns an individual deployment operation or task record. A replacement checks ownership and remote state before taking over; a returning agent must not compete. This does not create a global release owner or queue. Independent authorized deliveries retain their independence and real provider concurrency controls.

## 2. Read current references on every resumption

At task start and after a pause, handoff, restart, crash, reconnection, context loss or compaction, freshly read the full required references and existing checkpoint before changes or retries. Memory, cached excerpts, prior conversation and old receipts do not replace reading. Routine sequential calls during uninterrupted work are not new resumptions.

Read the four shared policies, repository/vendor/nested instructions for the actual affected paths, `PUBLISHING.md` when delivering, and area/blocker references explicitly required by those files. The index is a minimum map, not permission to omit an applicable instruction or scan every unrelated document. If a required reference is unavailable, try its verified canonical source; record the gap and do not perform dependent actions without it.

Use the directly invoked policy reader described in the reference index. After reading its full output and the remaining required files, record time, actual paths, policy version/hashes and relevant Git revision in the existing checkpoint. The generated receipt proves which bytes were emitted, not comprehension, compliance or that all running agents reread them. A drift check diagnoses mismatched copies; it never synchronizes or resets another checkout.

Before retrying interrupted work, recover checkout, branch, PR, owning run, selected component and installed migrations as applicable. Establish whether the action already completed. Preserve unknown/pending outcomes and operation identity.

## 3. Classify the actual delivery

**Non-engine work pushes, publishes, verifies and finishes through its normal route immediately, without waiting for `:55`.** Pages, buttons, styles, assets and clients using an already supported engine API do not require a new engine deployment. Repository name, generic health checks, another task's pending engine upgrade or an unrelated server commit on main do not establish a dependency.

Inspect the diff and connected behavior. Classify documentation, client, engine, database and delivery tooling separately. Identify any specific new engine contract and its source evidence before using it as a blocker. An unclassified path requires prompt investigation, not an automatic hourly wait. CI test selection and runtime activation are distinct: a client financial change can require database/server qualification without restarting the engine.

For client-only delivery, finish applicable checks, protected merge, static publication, both public build-info endpoints and affected behavior now. Table transport/gameplay presentation still requires applicable interoperability proof against the serving engine, without demanding an unrelated unshipped engine SHA. World Hub and Commander use their own normal routes. Split compatible independent portions of mixed work and record component results separately; retain actual schema, financial and compatibility prerequisites.

For engine work, push, check, merge, build and stage as soon as each prerequisite passes, throughout the hour. Only activation or behavior requiring the new engine waits for the maintenance owner's certified window. Build the immutable image before cutover. Immediately verify running identity and required local/public/database/behavioral proof after activation, retaining rollback time. Pre-cutover build success is not live proof. Record absolute window time and timezone; the clock alone never authorizes a restart.

## 4. Recover failed delivery immediately

Resolve the demonstrated blocker before optional improvements. Find the last successful comparable check/deployment and compare source, inputs, configuration and environment; state when none is available. Reuse the proven route and smallest supported correction. Repeated unchanged failure requires diagnosis, not blind retry or a replacement pipeline. Retain valid evidence for unchanged inputs; rerun affected checks and every check required for the final candidate.

| Authoritative outcome                           | Required next action                                                                                                                                    |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Build, test, configuration or preflight failure | Diagnose, fix, validate and promptly submit the eligible correction; no hourly cooldown for preparation                                                 |
| Transport timeout or unknown acknowledgment     | Read durable remote outcome and reattach to the same owning operation before any possible duplicate side effect                                         |
| Cutover failure                                 | Read serving version and owning transaction/recovery state; prepare correction and immediately reassess certificate and remaining proof/rollback budget |
| Published successfully but proof missing/failed | Verify exact installed/live state and repair or rerun appropriate verification; do not restart a healthy engine merely to regenerate evidence           |

A simple correction must not be parked until next hour. Record failure, diagnosis, fix-ready, corrected submission, admission and final verification times. Distinguish repair time, provider queue/execution, publication and actual activation constraints. “Waiting for next hour” alone is not a diagnosis: name the failed gate, safety budget and earliest eligible continuation.

The additional engine recovery opportunity must be implemented in the existing owning release/maintenance transaction with durable ownership, draining, database freeze, proof, rollback and v3 thaw. Preserve the two-minute last-hand lead, five-minute window and full 285-second cutover/rollback reserve; never overlap the next hourly announcement, prolong a prior freeze or restart active games to meet a speed target. Verify the connected implementation and installed contract before using it. Markdown and source merge alone do not prove runtime availability. No second publisher or recurring release repair mechanism may supply this behavior.

## 5. Continue eligible work while real dependencies run

Follow actual provider run/job results and logs. Distinguish failed tests from missing workers, wrong runner labels, dependency wait, provider concurrency and superseded attempts. Compare a current successful equivalent. Correct demonstrated configuration defects; retire only verified obsolete attempts of this same assigned PR through the approved operation. Confirm terminal cancellation, including `always()` jobs. Never cancel another task's current checks or production transaction to free capacity.

Check access early under the owner policy. If input/authentication or an explicit tool handoff is unavailable, name the exact capability, evidence and prepared next action. Continue independent checks, conflict repairs and eligible publication yourself. A pending question or running CI is not completion. End blocked only when no further authorized useful action remains, retaining the exact operation and what would unblock it.

While five minutes or more remain before an actual required cutover, choose a useful finite item from the existing acceptance checklist: missing evidence, connected defect, integration, verification preparation or a separately authorized next phase. Preserve the qualified candidate; keep candidate-changing work separate. Under five minutes, brief standby is permitted if ready and switching risks missing the window. Existing blocker recovery takes priority over optional improvements.

When nothing useful and authorized remains, say so and identify the external dependency. Do not invent work, repeat passed checks, send unchanged status messages, wait for optional help or start an indefinite audit to appear busy. Retain the pending run/revision and responsibility when switching to separately authorized work. No timer, watcher, cron or recurring agent may finish the release for you.

## 6. Report evidence honestly and finish

Use one existing checkpoint/report for tested revision/tree, required checks and actual commands/results, access prerequisites, provider-only pending checks, operation identities, component selection, installation and remaining live proof. Relevant changed inputs invalidate affected evidence. Missing, unreadable, cancelled or unexplained skipped checks are not passing. PR validation artifacts are never production artifacts.

Keep implemented, tested, hardened, regression-protected, merged, installed, published and verified live separate. A green job that deferred cutover, recovered previous engine, completed review or successful build is not the new release. Source-only instruction delivery does not require an engine cutover. Never declare an unqualified next phase ready or guarantee future failures impossible.

The evidence tools summarize supplied observations, with unknown timing left unknown; they are not a new approval gate or proof of universal agent behavior. Use current protected procedures and actual acceptance criteria to decide completion. Once sufficient scoped evidence exists, finish without another unnecessary sweep.
