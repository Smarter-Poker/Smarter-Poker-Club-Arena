## 1. The journal (`diamond_transactions`) as the earn engines see it

Columns: id, user_id, type, amount, balance_after, description, reference_id, created_at, transaction_type, source, metadata. Two type columns exist (`type` and `transaction_type`); the writers below set them inconsistently.

Constraints and indexes that matter for idempotency:

- `idx_diamond_transactions_reference_id` UNIQUE (reference_id) WHERE reference_id IS NOT NULL. GLOBAL, not per user.
- `diamond_transactions_user_reference_uidx` UNIQUE (user_id, reference_id) WHERE reference_id IS NOT NULL.
- CHECK `no_home_games_source` (source <> 'home_games').
- Triggers: `trg_ca_append_only -> fn_ca_journal_append_only` (no UPDATE/DELETE), `trg_enforce_anti_farming_caps -> fn_enforce_anti_farming_caps` (BEFORE INSERT, debit rows on gift/transfer channels only).

So: ANY writer that supplies a non-null `reference_id` gets DB-enforced idempotency for free (a second insert with the same reference fails). Writers that pass NULL reference_id get none. This is the single most important fact in this lane and the per-engine table in section 15 is organised around it.

## 2. Anti-farming (shared layer)

`fn_enforce_anti_farming_caps` (BEFORE INSERT trigger on diamond_transactions) fires only when amount < 0 AND (transaction_type IN ('live_gift_sent','diamond_gift_sent') OR source IN ('stream_gift','wallet_transfer','wallet_diamond_transfer')). It requires `metadata->>'recipient_id'` (raises check_violation if missing), bypasses sender `47965354-0e56-43ef-931c-ddaab82af765` (KINGFISH), then delegates to `fn_check_anti_farming_gift_cap(sender, recipient, amount)` and raises if not allowed.

`fn_check_anti_farming_gift_cap(sender, recipient, amount)` live constants: CAP_PER_PAIR_24H 5,000; CAP_PER_USER_24H 50,000; CAP_BURST_60S 2,000; CAP_FRESH_PAID_24H 500; TRUST_AGE_DAYS 120; NEW_USER_DAYS 30; PURCHASE_COOLDOWN_DAYS 7. Order of evaluation:

1. invalid args / self-transfer refused;
2. KINGFISH sender: allowed, no further checks;
3. sender banned by recipient broadcaster (`live_bans` join `live_streams`): refused;
4. `profiles.is_farming_flagged` true: no bypasses, caps apply;
5. unflagged AND first completed non-refunded `diamond_purchases` older than 7 days: ALLOWED, all caps skipped (`trusted_purchaser_7d_bypass`);
6. unflagged AND account age >= 120 days: ALLOWED, all caps skipped (`trusted_120d_unflagged_bypass`);
7. account < 30 days AND has purchased: 500 / 24h total out on gift channels (fresh-paid cap), then allowed;
8. otherwise: pair cap 5,000 / 24h (metadata recipient_id match), user cap 50,000 / 24h, burst 2,000 / 60s.

All windows are computed from `diamond_transactions` debit rows on the gift channels, so they are only as complete as the journal. There is NO device fingerprint, IP or account-linking check anywhere in this function; "linking" is limited to the sender/recipient pair sum. Velocity is the 60 s burst cap only. A 120-day-old unflagged account, or any account 7 days after one Stripe purchase of any size, has NO outbound cap at all. The 2-arg overload (sender, amount) is a legacy shape (1,835 chars) and is not what the trigger calls.

## 3. The shared mint primitive: `add_diamonds_to_balance(uid, amount, type, description, reference_id)`

Live body (SECDEF, service_role only), in order:

1. `v_exact_type := p_type IN ('trivia_entry','trivia_run','trivia_daily_bonus','trivia_prize_wheel','pvp_stake','pvp_win','pvp_refund','pvp_tie_refund','tournament_entry','tournament_entry_refund','tournament_cancel_refund','tournament_prize')`. Exact types with NULL reference_id are refused (`reference_id_required`, added by `pvp_refund_mint_leak` on 2026-08-23).
2. If reference_id is non-null and a row (user_id, reference_id) already exists in diamond_transactions: return `duplicate_reference` with the existing balance_after. This is a code check; the two UNIQUE partial indexes in section 1 back it at the DB level.
3. `SELECT diamonds, diamond_multiplier FROM profiles ... FOR UPDATE`.
4. Multiplier: applied only when amount > 0 AND NOT exact type AND p_type NOT IN ('purchase','deduction','adjustment','refund','transfer','diamond_gift_received','diamond_gift_sent','diamond_gift_refund','diamond_received','live_gift_received','live_gift_sent','vip_daily','vip_stipend') AND multiplier > 1.00; then `round(amount * multiplier)`. So the multiplier DOES apply to `daily_login`, `easter_egg`, `training_reward`, `video_favorite`, `bonus`, `earn`, `credit`, `daily_trivia`, `trivia_reward`, `endless_reward`, `survival_reward` etc. Journal metadata records raw_amount, multiplier, exact_value.
5. Refuses if new balance < 0 (`insufficient_diamonds`).
6. `UPDATE profiles SET diamonds, diamond_balance`; INSERT journal with transaction_type = type = p_type, `source` NOT set (hence NULL on every row in section 1).

NOT in this function: any read or write of `diamond_platform_budget`, any per-user per-day cap, any per-type daily cap. Budget and cap enforcement, where it exists, lives in the callers.

Migration `fix_transfer_multiplier_mint` (2026-08-03, in `supabase_migrations.schema_migrations`) is what added the transfer/gift types to the multiplier exclusion list, so a transfer credit can no longer mint via the recipient's multiplier THROUGH THIS FUNCTION. Section 11 checks whether the transfer functions actually route through it.

`profiles.diamond_multiplier` distribution: see section 3.1 query below.

### 4.3 The `pvp_refund` incident (488 rows, 14,240 diamonds, 08-13 to 08-23)

From the migration header of `20260823_pvp_refund_mint_leak.sql` (World Hub repo) and the live data:

- `/api/cron/trivia-pvp-cleanup` (moved to `smarter-poker-workers`) refunded every player of an abandoned match, then tried `status = 'abandoned'`, which the CHECK constraint rejected; the error was never read, the match stayed active, and the next tick refunded again: 4 matches x 2 players x every 4 hours = 48 rows/day (observed: 46 to 48 rows/day from 08-15 to 08-23). Refund written with NULL reference_id, so `add_diamonds_to_balance` dedup never fired.
- Journal now: 488 `pvp_refund` rows, all with reference `legacy_pvp_refund_incident_20260823_<id>` (back-filled by the migration), 384 x 10 (4 users) and 104 x 100 (2 users); 244 rows / 7,120 to humans and 244 rows / 7,120 to horses. Only 3 `pvp_stake` debits (120) were ever charged, so 14,120 was pure mint.
- Remedy in the same migration: CHECK widened to allow 'abandoned' and 'settling'; 4 matches closed; `add_diamonds_to_balance` now refuses positive settlement-type credits with NULL reference; clawback via `adjustment` rows (journal: 7 adjustment rows, -14,120 debited, +440 credited, net -13,680 in 30 days; the +440 is the netting of stakes actually paid).
- Lesson for the standard: the dedup existed but was OPT-IN (needs a reference). Every settlement credit now requires one; every OTHER type still does not.

## 5. Engine 3: reward catalog (`award_diamonds_v2`, `diamond_reward_catalog`) and the budget

### 5.1 `diamond_platform_budget`

Columns: period text, budget_diamonds bigint, spent_diamonds bigint, updated_at. Rows: 2026-07 budget 2,500,000 spent 21; 2026-08 spent 2,252; 2026-09 spent 220 (as of 16:37 UTC 09-02). Sum 7,500,000 / 2,493.

- What funds it: nothing. `award_diamonds_v2` does `INSERT ... (period, 2500000) ON CONFLICT DO NOTHING` at first use each month; the 2,500,000 is the constant `c_platform_budget` in the function body. It is a COUNTER with a ceiling, not a liability account: no mint ledger row, no treasury debit, no `ca_mint_ledger` entry backs it.
- What reads/writes it: exactly one function, `award_diamonds_v2` (`SELECT ... FOR UPDATE` on the period row, then `spent_diamonds = spent_diamonds + v_award`). No trigger on the table. No other engine debits it: trivia, daily challenges, memory game, streak, share streak, signup, union payouts and every legacy `fn_add_diamonds`-style writer are all OUTSIDE the budget.
- Consistency check: 30-day journal credits for the v2 action keys (daily_login 1,467 + easter_egg 960 + training_reward 32 + video_favorite 1 = 2,460) vs budget spent Aug 2,252 + Sep 220 = 2,472 (the window differs by a few days). Consistent within the window difference.
- Side effect worth knowing: the `FOR UPDATE` on the single period row serialises EVERY award_diamonds_v2 call platform-wide through one row lock.

### 5.2 `award_diamonds_v2(uid, action_key, reference_id, target_id, metadata)` live body (SECDEF, service_role; 16,903 chars compact)

Constants: catalog_version 3; platform budget 2,500,000/month; login ladder base 10, step 5, max 110; egg monthly 1,000 and single max 1,000; streak_reward monthly 1,000; daily_bonus monthly 3,750 (single max 125); training_reward monthly 1,500 (single max 50); achievement monthly 1,000 (single 500); challenge monthly 1,000 (single 500); tournament_prize single max 10,000, NO monthly cap.
Flow: catalog lookup (`active = true`) -> profile read (NO `FOR UPDATE`) -> VIP check (`is_vip` and lifetime or unexpired) -> daily cap 110 (VIP 150) and monthly cap 3,300 (VIP 4,500) computed from journal rows whose transaction_type joins a `counts_toward_daily_cap` catalog key -> per-action `max_per_day` by counting journal rows of that transaction_type today (America/Chicago day) -> `lifetime` keys: refused if any positive row of that type exists -> reference_id dedup if supplied (EXISTS on (user_id, reference_id)) -> action-family amount logic -> multiplier -> LEAST(daily remaining, monthly remaining) -> budget `FOR UPDATE`, LEAST(budget left) -> `UPDATE profiles SET diamonds = v_new_balance` -> journal row with transaction_type = type = action_key, description "Diamond Rewards v2: <key>", metadata carrying catalog_version, requested, awarded, capped, multiplier, category, streak, is_vip -> `EXCEPTION WHEN unique_violation` returns `duplicate`.
Journals: yes. Idempotent by constraint: yes WHEN the caller passes a reference_id (the two UNIQUE indexes); `max_per_day = 1` keys are ALSO effectively idempotent per day because the count is computed from the journal, but that is a code check under no lock other than the budget row (the budget FOR UPDATE happens AFTER the count, so two concurrent calls can both pass the count and both award; the reference_id path is the only race-free one).
Defect: the profile balance is read without a lock and written back as an absolute value. Any concurrent writer on the same profile (a transfer, a purchase, `add_diamonds_to_balance`) between the read and the write is silently overwritten. Low probability at current volume, but it is a lost-update bug on the canonical store.

## 16. Anti-farming picture

What exists: one shared cap function (`fn_check_anti_farming_gift_cap`, 3-arg) called both by the atomic send functions and by a BEFORE INSERT trigger on the journal; caps pair 5,000/24h, user 50,000/24h, burst 2,000/60s, fresh-paid 500/24h; a `profiles.is_farming_flagged` switch that removes all bypasses; broadcaster bans honoured; the KINGFISH account exempt everywhere. The in-use API routes add JS-side sums and, for live gifts, an IP-based check (`sum_anti_farming_ips`).
What does not exist: any device or account linking, any check on the RECEIVING side (a farm of fresh accounts sending to one collector is bounded only per sender), any cap once an account is 120 days old or 7 days past a single purchase of any size, any cap on the legacy `transfer_diamonds_*` pair (trigger does not match its rows), any velocity limit on EARN engines (trivia awards, daily challenge claims, union grants and referral bonuses have no per-day count), and any reversal window on transfers. The KINGFISH bypass is a hard-coded uuid in two functions.
Referrals are the obvious farm: `referral_bonus` 100 + 50 per referee via `add_diamonds_to_balance` (outside v2 caps and budget), plus the catalog's `referral_qualified` / `referral_vip_conversion` 500 x 20/day outside the daily and monthly caps. Nothing in the DB ties a referral award to a verified, funded or aged referee; UNVERIFIED what `social/referral.js` checks in JS.

## 17. Gap list against the target standard

Target A: a budget per source with hard caps.

- A1. Only `award_diamonds_v2` debits `diamond_platform_budget`; trivia, tournaments, daily challenges, memory, share streaks, referral bonuses, promo redemptions, union grants and the signup grant all mint outside it. Budgeted issuance in 30 days: 2,460 of 16,740 journaled credits (15 percent), and 0 of the 208,000 seeded.
- A2. The budget is a counter (constant 2,500,000/month written by the function itself), not a liability funded from the Mint; nothing in `ca_mint_ledger` backs it and nothing reconciles `spent_diamonds` to the journal.
- A3. Inside v2, `referral_qualified`, `referral_vip_conversion` (500 x 20/day) and `vip_stipend` (500/day) are excluded from the daily/monthly caps and have no family cap; `tournament_prize` has no monthly cap.
- A4. Daily challenges carry no cap at all: 2,463,304 diamonds were offered in snapshots in 30 days against a total supply of 1,030,092; 897,095 is already completed and claimable.
- A5. The trivia tournament fee cut (floor(10 percent)) is burned, not banked; 216 diamonds across the three completed events vanished with no ledger line.

Target B: award idempotency per (user, source, event) by UNIQUE.

- B1. The journal has the right indexes (UNIQUE (user_id, reference_id) and a global UNIQUE (reference_id)), but idempotency is OPT-IN: every writer that passes NULL reference_id (memory game, legacy transfer pair, `award_diamonds`, `fn_add_diamonds`, `fn_credit_diamonds`, `increment_diamonds`, union grants, trivia_arcade/game_cost debits) gets none. `add_diamonds_to_balance` refuses NULL refs only for the 12 settlement types.
- B2. `award_diamonds_v2` `max_per_day` / `lifetime` are journal COUNTS under no lock (the budget FOR UPDATE comes after), so two concurrent calls without a reference can both award.
- B3. `send_wallet_diamond_transfer` / `send_stream_gift` dedup pre-check compares the bare reference to suffixed rows and never matches; the UNIQUE index saves the money but the client gets an error instead of `{duplicate: true}`; a NULL client reference becomes a fresh uuid, so retries double-send.
- B4. The global UNIQUE on reference*id means two different users can never share a reference string; writers that build references without the user id (`challenge_claim_batch:<request_id>:diamonds` is fine; anything like `easter_egg*<slug>` would not be) must be checked before the standard mandates a format.

Target C: catalog versioned and logged.

- C1. `diamond_reward_catalog` (32 rows) has no version column, no history table, no trigger; `catalog_version = 3` is a constant in the function, not in the table. `daily_challenge_catalog` (58 rows) and `trivia_diamond_award_limits` (20 rows) likewise. A catalog edit changes payouts with no record.
- C2. The function overrides the catalog for `daily_login` (ladder 10..110 vs row 5) and reads amounts for 8 keys from caller metadata (`egg_diamonds`, `streak_diamonds`, `bonus_diamonds`, `reward_diamonds`, `achievement_diamonds`, `challenge_diamonds`, `prize_diamonds`), so the catalog is not the source of truth for those keys either.
- C3. Two more catalogs are dead but live: `reward_definitions` (106 rows) behind `claim_reward` (credits a mirror), and `diamond_reward_claims` (154 rows, no writer).

Target D: promotional issuance tracked separately from purchased.

- D1. The journal has `source` (NULL on 570 of 570 rows in 30 days) and two type columns set inconsistently (`type` only by the legacy writers, `transaction_type` only by some, both by `add_diamonds_to_balance` and v2). There is no `issuance_class` (promotional / earned / purchased / transferred / seeded) anywhere. Purchased diamonds (`diamond_purchases`, 3 rows / 300, per the brief) are indistinguishable in the journal from a promo grant except by type string.
- D2. 208,000 diamonds seeded to horses since 09-01 and the human welcome 500s are not journaled at all, so the largest promotional source has no row to classify.
- D3. `ca_diamond_balance_audit` misses INSERTs (trigger is AFTER UPDATE OF diamonds), so a balance born non-zero is invisible to the audit as well as the journal.

Target E: P2P double-entry, capped, logged, reversible in a window.

- E1. The atomic double-entry functions exist and are correct in shape but have never been called; production uses the two-transaction `deduct_diamonds` + `add_diamonds_to_balance` path, whose historical signature is 6 debits vs 3 credits (-10,155 vs +10,135) on `diamond_gift_*` and 11 vs 13 (-160 vs +175) on `live_gift_*`.
- E2. The legacy `transfer_diamonds_deduct/credit` pair is still executable by service_role and is invisible to the anti-farming trigger.
- E3. `fn_union_send_to_member_zd3core` with kind diamonds is a one-sided credit of up to 100,000 per call with no debit, no reference and no dedup; the permission check is skipped for the service role, so the API route is the only guard.
- E4. No reversal window, hold, or refund function exists for any transfer; `diamond_gift_refund` / `live_gift_refund` are compensating credits the API issues when its own second call fails.
- E5. Caps vanish entirely for accounts >= 120 days or 7 days past any purchase; recipient-side aggregation does not exist.

Target F (Dan's law 10.5, horses): the DB treats horses identically wherever it is the actor (tournament payouts, challenge assignment); every browser-triggered earn (login, eggs, shares, memory, and the challenge Claim button) has no engine-side equivalent, leaving 897,048 diamonds of horse challenge rewards permanently unclaimable and 0 horse earn rows in 30 days.
