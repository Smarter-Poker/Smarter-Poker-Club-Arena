# Valid Spin draws were rejected after every database round trip

At 18:29 UTC, four minutes of bounded production logs contained 2,172 matching Spin draw proof failure lines. The manager wrote the draw three times, rejected every read-back and stood down; the next admission repeated that loop. The database showed sampled tournaments 4d8451e2-6333-40fb-9898-ff9312482c40 and c552817c-94f4-484f-88d4-10f74f4029ec still REGISTERING with a multiplier, prize pool and populated blind/payout structures. This is separate from the delivered-add-on settlement blocker, which was fixed and naturally cleared at 18:09.

The read-only production catalog confirms blind_structure and payout_structure are TEXT, spin_locked_tiers is JSONB, prize_pool and spin_multiplier are numeric, and spin_reveal_at is timestamptz. launchRowMatchesPatch compared JSON.stringify(actual) with JSON.stringify(expected) for objects. A saved text array therefore never matched the expected JavaScript array. Native JSONB could also fail solely because object key insertion order changed.

The fix decodes JSON text before deep strict comparison. Array order, every nested key and value, multiplier, pool, stack, reveal timestamp and booleans remain part of the proof. Malformed JSON and different content still refuse launch. It also requires the selected column to exist and prevents null, booleans or blank strings from being coerced into a numeric zero proof. The launch receipt, three-attempt write limit, lifecycle checks, money booking and stand-down behavior are unchanged.

The real manager proof is exercised without creating a tournament or making any live mutation. Seven assertions failed before the change: the two valid database representations and five overly permissive missing/numeric cases. All 20 read-back scenarios pass after the change; 34 existing Spin/tournament integrity guards also pass, for 54 total. Server tsc --noEmit exits 0.

At 18:29 the reported cash table had completed 28 further hands since the add-on fix. Fleet completion-to-deal sampling still showed p50 2,970 ms, p90 8,540 ms and maximum 41,488 ms. The repeated Spin launch writes are a concrete unnecessary database load; their contribution to those hand delays remains an inference until the corrected engine is deployed and sampled. The release and post-deployment Spin progression must still be verified through the announced Hetzner maintenance path.
