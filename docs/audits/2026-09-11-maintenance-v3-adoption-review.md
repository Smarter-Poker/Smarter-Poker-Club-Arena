## Proposed integration behavior

The patch changes only the maintenance callback in GameServer, MaintenanceBreak identity/release handling, the maintenance store's narrow release read, and the local reconnect duration cap. It consumes the unused strict helper already saved separately.

- Send one immutable five-argument identity and retry only that identity. Validate both returned identities, release flags/reason, every required completed step and consistent endpoint/duration. A void callback or legacy aggregate result cannot authorize production resume.
- Keep local pause ownership through the future endpoint, then re-read the narrow database witness until it returns null. A fast host clock cannot open the gate while the database still reports a future certificate.
- Abort retry delays and release waits when this process lifecycle ends. An explicit SQL ownership/identity/legacy-checkpoint refusal leaves the break held; it never falls back to three arguments or clears the row.
- Claim expired durable rows and drive the same v3 thaw path. No row-age shortcut clears a freeze. A row-deleted boot can hold on the public future-release witness without inventing a token, announcement or thaw receipt.
- Keep unknown recovery reads held and retry them. Transient thaw attempt failures retry under the same owner; bounded helper failure is not release. The v3 transaction owns durable deletion, so the engine does not separately clear its row after receiving a release receipt.

## Approval boundary and remaining verification

Automatic approval review rejected the local runtime edit with the stated concern that this broadly changes maintenance thaw/recovery behavior and could keep live tables paused or disrupt releases. The reviewer said general Phase 3 authorization did not cover this unverified service-wide implementation. The rejected edit was not run, was not retried through another tool or checkout, and no production or native database action occurred. Specific approval is required before applying and executing this integration.

This is a review candidate, not deployable evidence. The largest operational change is retaining pauses when a thaw or release is unproved, matching the current database freeze. A permanently refused legacy partial checkpoint can therefore require an explicit operational decision; automatically minting v3 target receipts or returning to the old bridge would violate the proved contract. Engine rollout must avoid an in-flight legacy checkpoint, or retain a specifically reviewed legacy completion procedure. The patch does not implement that procedure.

After approval and context reconciliation, meaningful acceptance must cover the full real MaintenanceBreak plus runtime callback, not only the helper:

1. complete=true with a future endpoint keeps both pause owners held; database witness remains future despite an advanced local clock; null witness then releases once.
2. Transport loss after commit recovers the exact receipt; cancellation during an RPC, retry delay or release wait never wakes or clears from the retired lifecycle.
3. Replacement claims an old countdown and an expired last-hand row, retaining the true freeze start. A freeze longer than 900 seconds credits reconnect suffixes once.
4. No-row boot with a future certificate holds without fabricating ownership; unreadable recovery state stays held and later recovers. Verify the narrow reader's process-root actor envelope.
5. Wrong owner/identity, malformed receipt, missing target step and legacy partial checkpoint cannot clear or resume. A new owner's state is untouched.
6. Adapt existing maintenance fixtures to explicit matching synthetic release receipts and release-boundary reads. Replace superseded age-clear/fail-open expectations with tests of the proved current contract; retain independent pause, durable save, countdown, restart and timer tests.
7. Re-run full server TypeScript and the real hand/manager CA09 composition against the integrated sources, then combine with root's current native thaw proof. Current helper PASS16 and earlier runtime PASS2 are separate evidence, not full integrated acceptance. Root separately reports current native thaw PASS for 300-second and 1,200-second scenarios in `2026-09-11-phase-three-current-thaw-native.json`; that database proof does not execute this unapplied runtime integration.
