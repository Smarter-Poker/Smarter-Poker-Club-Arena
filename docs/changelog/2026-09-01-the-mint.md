# The Mint

Dan, 2026-09-01:

> somewhere I can create chips and diamonds and send them directly to players,
> clubs etc, so there is never a "drift" or a flag for where did these chips
> come from.

That is the right instinct, and it is the answer to most of what has been on the
incident board today.

## Why the drift kept happening

Chips have been appearing in wallets, treasuries and agent banks all day through
provisioning scripts, restores and direct balance writes. The platform could
only ever report them **after the fact**, as "unexplained supply" or
"unclassified flow", because chip creation had no front door. There was nothing
to distinguish a deliberate act of issuance from a leak.

The problem was never that someone created chips. Dan is allowed to create
chips. The problem was that creation looked exactly like a bug.

## What The Mint does

`fn_ca_mint` declares `issuance_reserve` as the counterparty **before** it
writes, so the movement lands in `chip_ledger` as

```
issuance_reserve -> player_wallet | club_treasury | agent_wallet | union_wallet
```

and `fn_ca_supply_snapshot` counts it as ledgered issuance **in the same
interval the balance moves**. Supply reconciles by construction. There is
nothing to explain later because it was explained as it happened.

Diamonds work the same way against their own journal: `fn_ca_diamond_snapshot`
explains diamond supply from `diamond_transactions`, so a diamond mint writes
that row in the same statement it moves the balance.

## What it refuses

- anyone who is not an `admin` or `god` (or `service_role` for automation)
- a missing reason, or one under ten characters. Why is not optional for issuance
- a missing idempotency key. A replay of one returns the original result rather
  than minting twice
- an amount that is not positive, not two decimal places, or over the per-call
  cap (1e9 chips / 1e7 diamonds)
- a destination that does not exist, or a player/agent wallet in a club they are
  not in. It will not invent a wallet to mint into

It **creates**; it never transfers. Moving chips between existing holders is
what the club bank, union send and agent wallet paths are for.

## Proven before it went live

Probed inside a rolled-back transaction:

| check                    | result                                            |
| ------------------------ | ------------------------------------------------- |
| non-admin caller         | refused, `the_mint_is_admin_only`                 |
| chips to a club          | `issuance_reserve -> club_treasury category=mint` |
| same op_id replayed      | `replayed=true`, balance unchanged                |
| chips to a player wallet | credited                                          |
| diamonds to a player     | journalled, `source=the_mint`                     |

## The page

`/hub/club-arena/mint`, mobile first at 375px. Asset toggle, destination, a
search for the player, club or union, amount, reason, and a running list of what
has been minted recently. Authorisation is the database's job, not the page's:
the page only reports what `fn_ca_mint` says.

## One fix that came out of building it

`fn_ca_money_rpc_drift` flagged `fn_set_club_lobby_message` as an unregistered
balance writer. It writes `lobby_message`. The sweep was matching on the **table**
alone, so any function containing `UPDATE clubs` counted as a money path.

That is not harmless: a checker that cries wolf on a lobby message teaches people
to register whatever it names, and the registry is only worth something because
each entry was audited. It also gates epoch-3 preflight, so a false positive
blocks a real gate. It now requires the table **and** a column that actually
holds a balance, with the column list derived from the live `fn_ca_autoledger`
triggers so it follows the schema instead of drifting from it.
