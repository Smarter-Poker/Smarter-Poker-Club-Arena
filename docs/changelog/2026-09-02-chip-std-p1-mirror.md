### How the 110 were exported

Read over a read-only `pg` connection from Dan's Mac
(`SET default_transaction_read_only = on`, application*name
`chipstd-p1-mirror-export-readonly`), directly from
`supabase_migrations.schema_migrations.statements`. Each file is
`supabase/migrations/<version>*<name>.sql`holding`statements.join('\n') + '\n'`, which is exactly what
`scripts/dev/export-applied-migrations.sh` writes
(`array_to_string(statements, E'\n')`) and what
`scripts/ci/backfill-unrecorded-migrations.mjs`writes. Every file carries the
repo's four-line`-- BACKFILLED ...`header above the applied text, because
that first-line marker is how`check-migrations-applied.mjs`and`check-definer-authorization.mjs` recognise a recovered record of an
already-applied migration (an object it declared may since have been dropped
or superseded; the applied text is still the correct record). The applied
statements themselves were not edited by a byte. No REVOKE/GRANT appendix was
needed on any file: with the marker in place every pre-push and CI gate
passed on the bodies as applied (`check-new-migration-version-collisions`: 110
new, all unique; `check-required-columns`, `check-title-case`,
`check-ui-text`, `check-no-emoji`, `check-no-orphaned-work`: OK).

One applied body (`20260902044316_rake_ledger_club_isolation_hard_guard`)
contains an em dash inside a SQL comment. It ran that way; it is left that
way, as the other 590 migration files on main that carry one are. The no-em-dash
gates read `src/`, `public/` and `server/src`, not migrations.
