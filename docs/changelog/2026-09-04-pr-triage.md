# 165 open pull requests, and how to tell which ones still hold work

## The measurement

| time since last update | Club Arena PRs |
| ---------------------- | -------------- |
| under 1 hour           | 9              |
| 1-6 hours              | 5              |
| 6-24 hours             | 27             |
| 1-3 days               | 30             |
| **over 3 days**        | **94**         |

165 open. **Of the 71 updated inside 72 hours, 55 are already `dirty` and 16
`blocked` - none are mergeable.** World Hub, same agents and same rules, has
**6 open, median age 12 minutes, zero conflicts.**

That contrast is the finding. Conflicts are not concentrated on a hot file
(5 PRs on ClubHomePage.tsx, 4 on GameServer.ts, spread thin from there) - they
are a function of TIME. Main takes about 125 merges a week; a branch that sits
for a day is racing forty of them. **A pull request that merges in ten minutes
cannot conflict with anything.**

## Dan's rule

> "SOME OF THE PRs I STARTED YESTERDAY, RAN OUT OF CLAUDE TOKENS AND HAVEN'T
> MADE IT BACK YET, SO THESE ARE PROBABLY GOOD, ANYTHING OLDER THEN 72 HOURS =
> BAD."

So the age threshold is **72 hours**, not 24. Under it is live work waiting for
its author to come back. Over it is not.

> "I SOMETIMES DO HANDOFF PROMPTS, SO OTHER AGENTS PICK UP WHERE THE OTHER
> AGENT LEAVES OFF. SO SOME MIGHT TRULY BE DEAD BECAUSE ANOTHER AGENT FINISHED
> THE JOB."

That is the case age alone cannot see, and it is why this needs a content test
rather than a timer.

## The discriminator

`.github/scripts/pr-triage.sh` classifies without closing anything. Two
independent signals, because neither is sufficient alone:

1. **`git cherry origin/main <branch>`** compares **patch ids**, which are
   content. It sees work a second agent landed under a different SHA - the
   handoff case - where `git log` sees nothing.
2. **`git diff -w origin/main...<branch>`** counts what is genuinely still
   unmerged, so a branch that was _reimplemented_ differently still shows its
   real size.

Measured on two known cases:

| PR                                                       | commits | unmerged by patch-id | net lines | files |
| -------------------------------------------------------- | ------- | -------------------- | --------- | ----- |
| #2067 (superseded, closed by hand earlier with evidence) | 1       | 1                    | **4**     | 1     |
| #2887                                                    | 2       | 2                    | **1308**  | 15    |

Note what that shows honestly: patch-id did **not** mark #2067 as upstream,
because the second agent reimplemented rather than cherry-picked. The line
count is what separated them, by a factor of 300.

Verdicts, and what each permits:

| verdict      | meaning                                   | may be auto-closed?   |
| ------------ | ----------------------------------------- | --------------------- |
| `SUPERSEDED` | every commit already upstream by patch id | yes, after archiving  |
| `EMPTY`      | no diff against main at all               | yes, after archiving  |
| `THIN-OLD`   | under 10 lines and over 72h               | **no** - review first |
| `OLD-WORK`   | real unmerged lines, over 72h             | **no** - Dan's call   |
| `LIVE`       | inside 72h                                | **never**             |

It fails closed: if `gh` cannot list pull requests, or the list comes back
empty, it exits non-zero rather than classifying on a partial view. A sweep
that reads "nothing to do" from a broken API call would close nothing today and
everything tomorrow.

## What it does NOT do

It does not close, comment, or delete. Closing is a separate deliberate step,
and only ever after the branch is archived to `refs/archive/<name>@<date>` -
the pattern already in `.github/scripts/archive-stale-branches.sh`. Nothing in
this repo should destroy an agent's only copy of its work.
