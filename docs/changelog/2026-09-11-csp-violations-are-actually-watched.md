# CSP Violations Are Actually Watched

Before: the World Hub has served `Content-Security-Policy-Report-Only` for the whole smarter.poker origin since Phase 6.1.14, and next.config.js says next to it that the plan is to "switch to Content-Security-Policy" once violations "have been monitored and confirmed zero". That monitoring never happened, because the policy carries no `report-uri` and no `report-to`. A report-only policy with nowhere to report is a policy that writes its findings to one line of one browser console and then forgets them.

The same file already documents what that costs. Sentry's ingest host was missing from `connect-src` from the day Sentry was added until 2026-08-29, and the comment written when it was fixed says the only symptom was "a line in the console that nobody reads" — and that flipping the header to enforcing in that state would have blocked every Sentry envelope on the platform and taken error reporting dark at exactly the moment a security header changed. Ten days, under a header whose entire job was to notice.

Correction: tests/e2e/production-csp-violations.spec.ts drives deployed production and writes down what an enforced policy would block. It needs no header rewriting and no cooperation from the Hub, because a browser fires `securitypolicyviolation` for a report-only policy too, with `disposition: "report"`. The spec signs in through the suite's own globalSetup, visits five Club Arena routes and three World Hub routes, scrolls each to the bottom so lazily mounted panels fetch their own things, collects every violation event, prints them grouped by directive and blocked URI, and fails if the list is not empty. It submits nothing and changes nothing.

The Hub routes are in there deliberately. The policy is set for the whole origin, so a Club-Arena-only sweep would certify a header that mostly governs somebody else's pages.

A second assertion covers the way the first one could pass for the worst possible reason. If the policy stopped being served at all, there would be no violations to collect and the sweep would go green on a site with no CSP. So the spec also reads the response headers and requires that a policy of either kind is present, that it still carries `default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'` and `frame-ancestors 'self'`, that Sentry ingest is still in `connect-src`, and that `upgrade-insecure-requests` is still in the ENFORCED header — it is ignored inside a report-only policy, which is why it lives separately, and nothing was checking that it stayed.

Verification: run against https://smarter.poker with a real authenticated session (globalSetup reported "direct Supabase session accepted by production"), both tests pass. Zero violation events across all eight routes — `/hub/club-arena`, `clubs`, `wallet`, `profile`, `promotions`, and the Hub's `/`, `/diamonds` and `/games`. That is the first time the question the next.config.js comment asks has actually been answered with evidence rather than with silence.

Wiring: the spec joins the post-deploy sweep, so the answer is re-measured against production after every publish rather than once. The lasting value is not today's zero — it is that the next external resource somebody adds without an allowance turns the sweep red the same day, instead of living in a console line for ten.

Scope note: this changes no header. Moving directives from the report-only policy into the enforced one is a World Hub change and is being made there, separately, and only for the directives that govern injection rather than resource loading.
