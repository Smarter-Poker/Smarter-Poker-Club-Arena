# The error reporter was the second-largest bug in the table, and it hid the first

Two families of unresolved rows in `horse_bug_reports` — `Unhandled Promise Rejection` (2,906) and `Uncaught Error: Uncaught TypeError: Cannot set property message of  which has only a getter` (2,686) — were one mechanism, end to end.

`OfflineQueueService.getCount()` called `db.transaction()` inside a `new Promise` executor that took no `reject`. IndexedDB raises `InvalidStateError` from that call synchronously once the connection is closing, and a throw inside an executor rejects the promise, so the call that was written to never fail became an unhandled rejection instead. `OfflineQueueBadge` polls it every 2000ms without a catch, so one closing connection produced one rejection every two seconds for as long as the tab stayed open.

`main.tsx` handed each rejection to `reportError`, which assigned to `message` while normalising it. `DOMException.prototype.message` is an accessor with no setter and modules are strict, so the assignment threw back out of the `unhandledrejection` listener — before `event.preventDefault()` and before `captureException`. The browser re-raised the reporter's own `TypeError` through `window.onerror`, and `HorseBugReporter` filed that as a second, critical bug whose title carried the word "Uncaught" twice.

The arithmetic is the proof rather than the theory. 2026-04-02, one 98-minute session: 2,686 IndexedDB rejections and 2,686 getter errors, 30–32 rows a minute, which is the badge's 2000ms poll counted. 2026-08-29, one Safari session: 158 and 158, the same defect worded `Attempted to assign to readonly property.` by the other engine and therefore filed under a second title. Exactly one secondary row per rejection. The ~62 rejections in the table that are not DOMExceptions produced no secondary row at all, because a plain `Error`'s `message` is a writable own property and the assignment succeeded.

**None of the 2,844 underlying IndexedDB failures ever reached Sentry.** The throw was on the line before `captureException`, so the only trace of the real fault was the reporter complaining about itself. That is the damage worth naming: a reporter that throws does not add an error, it replaces one, and every caller of `reportError` is a `catch` block that was handling something specific.

Fixed at all four points. `errorReporter` computes strings instead of assigning to properties it does not own, guards every read and conversion that has thrown in production (`String` on a Symbol, `JSON.stringify` on a circular object, a hostile `message` getter), and wraps its whole body so a defect in the reporter degrades the report rather than replacing the caller's error. The queue's readers resolve rather than reject when the connection is closing, matching the decision their own `onerror` handlers already made. The rejection is marked handled before anything that can fail runs. And `window.onerror` titles no longer prepend a second "Uncaught" — which, since #4398 made the title the dedupe fingerprint, was filing one defect as two permanently separate rows.

`tests/a-reporter-does-not-become-the-bug.law.test.ts` pins all four. It reproduces the platform shape explicitly: happy-dom gives `DOMException` a writable own `message`, so a test built on the stock object asserts nothing — checked against the exact 2026-03-30 source that caused the burst, it passed.
