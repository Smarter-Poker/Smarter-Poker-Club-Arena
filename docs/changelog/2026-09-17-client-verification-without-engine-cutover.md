# Client verification completes independently of engine cutover

The static publisher already operated throughout the hour. The post-publication workflow did not: its single browser job resolved the newest server revision on protected main and refused to run any client checks until that exact engine was live. An unrelated staged engine upgrade therefore prevented verification of a normally published client.

The existing event-triggered workflow now has independent client and live-table jobs. All prior schema, financial, browser and actual-hand/reconnect checks remain; each job retains authenticated reserved-account setup/cleanup, strict reports and client revision provenance. The table job only spectates existing games with its own randomly generated reserved identity, so it has its own serialization group instead of occupying the stateful client fixture lock. Neither job waits on the other. No new workflow, schedule, publisher or automatic repair was added.

After a client publication, the table job records the healthy engine actually serving production and verifies its full revision belongs to protected main. The exact engine gate and per-observation checks then require that revision throughout certification. After an engine release event, it requires the event's immutable revision instead; an older engine still fails. Ordinary client checks do not request engine health or resolve an engine target. Table-affecting client changes still require their applicable interoperability proof.

Regression qualification executes the maintained resolver and admission shell in an isolated Git repository with an older serving engine and a newer pending engine on main. The previous client path selected the pending revision and failed; the corrected path selects and admits the serving revision. The engine event continues to select the requested new revision and rejects the older serving engine. Wiring checks retain separate results, report enforcement, cleanup, concurrency and exact provenance. Local and hosted results, protected integration and live execution are recorded separately in the task evidence; source alone is not production proof.
