# The Health Watch Resolves What It Filed, The Transfer Door Is Named, DR16 Has A Consumer

Date: 2026-09-19. Branch: `agent/cw-diamond-gate/fix/the-health-watch-resolves-what-it-filed`. Two forward migrations, two isolated Postgres 17 runners, two laws. No client or engine change. Both arena switches stay off.

## What was wrong

Three things, all read against production on 2026-09-19.

**The release gate was jammed by its own detector.** `ca_diamond_incidents` held 45 open rows with `severity = 'critical'`, every one `DR0:health_critical`, filed hourly by `fn_ca_diamond_health_watch` between September 9 07:35 and September 11 15:35 UTC. Their causes, read from each row's detail, were 36 rows of horse rewards expired unclaimed on 09-09 and 09-10, 9 rows of trial balance, 8 rows of a -100 money-identity difference on 09-11 and 2 rows of an unexplained deploy gate. Every one of those areas had read `ok` from `fn_ca_diamond_health()` since 09-11 16:35. Eight `DR11:trial_balance_break` warnings from 09-11 were open too, with the trial balance at 0 on every account since. Nothing in the estate resolves a DR0 row. The programme's public-release condition is "seven consecutive clean trial-balance days, zero suspense and no open critical `ca_diamond_incidents`"; the streak stood at eight days and these rows were the only thing keeping the gate literally unmet.

**The player-to-player transfer had never worked in production.** `send_wallet_diamond_transfer(uuid,integer,text,text)` (ruling 4, amended 2026-09-08; restored by 20260909200327) runs under the sender's JWT and writes both wallets itself, and `fn_guard_profile_privileged_columns` refuses any write to `profiles.diamonds` that is not service-role and not made from a call stack naming a listed money RPC. The route was not listed. Every transfer a player attempted since 09-09 answered 42501 at the first wallet UPDATE and rolled back: `diamond_wallet_transfers` held 0 rows, ever. The Phase 4 acceptance ran on an isolated fixture that carried no profile guard. `fn_ca_diamond_unreachable_money()` had reported exactly this (`client_reachable_but_guard_refuses`) since it was written, and the earlier audit's "52 transfers in 30 days" were rows of another path with no source, not this door.

**DR16 had no consumer.** `DR16:deposit_inside_settlement_window` (ruling 14: a purchased lot younger than the settlement window is not depositable) was consumed by `fn_arena_deposit`, which the custody model replaced. The daily arming sweep would have tried to arm it on 2026-09-22 and been blocked by "no function consults this rule".

## What changed

`20260919223032_the_health_watch_resolves_what_it_filed.sql`: `ca_diamond_incidents` gains a nullable `resolution` text column. `fn_ca_diamond_health_watch`, after filing exactly what it files today, resolves every open DR0 row whose named areas all read something other than critical or unknown on this tick, with a note naming each area and what it read; a row with any area still critical stays open; a row naming no area is left for a person; an empty report clears nothing. `fn_ca_diamond_trial_balance_watch` resolves an open DR11 break when its account reads difference 0 and an open DR12 suspense row when suspense reads 0; its seven-day and thirty-day info housekeeping is reproduced byte for byte. Both live bodies are md5-pinned before they are replaced. The migration ends by running one tick of each watch through the deployed code and refuses to commit if any critical incident is still open, so the gate cannot be met by a migration when a real critical cause is present.

`20260919223115_the_transfer_door_is_named_and_dr16_has_a_consumer.sql`: one line is added to the profile guard by marker against its live body (md5 pinned, substitution proved reversible) naming `send_wallet_diamond_transfer`, after checking the route's own md5, its live-session requirement, both journaled legs and its grants (authenticated yes, anon no). `fn_poker_diamond_reserve`, the deposit door every buy-in and tournament entry passes through, already refused an unsettled lot as `insufficient_settled_diamonds`; it now reads `fn_ca_diamond_rule_mode('DR16:deposit_inside_settlement_window')` so the rule has a consumer. The refusal stands in both modes, because the settled-lot reservation that follows draws only on settled lots and an unsettled lot admitted in log mode would sit in custody with nothing for a chargeback to find. Armed, the same refusal is raised under the rule's own code `P0416` with a DETAIL naming the rule and the amounts; the leading token the engine and client match on does not change. Both functions are on the guard watchlist and their redefinitions are declared through `fn_ca_declare_guard_redefinition` in the same transaction. The migration reads `fn_ca_diamond_unreachable_money()` and refuses to commit if either finding is still listed.

- Laws `tests/a-diamond-incident-cannot-outlive-its-cause.law.test.ts` and `tests/the-transfer-door-is-named-and-dr16-has-a-consumer.law.test.ts` pin the migration text.
