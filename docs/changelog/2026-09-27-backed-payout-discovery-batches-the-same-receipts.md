# Backed payout discovery reads each receipt set once

The existing hourly job calls the default, non-applying form of `fn_pay_backed_payout_shortfalls`. Its selection invokes the scalar conservation calculation separately for every eligible completed event in the unchanged 30-day window. A small final result limit cannot avoid that work, and the provider job repeatedly reaches its 120-second deadline.

The replacement batches only the discovery SELECT. It materializes the exact filtered wallet receipts, groups the same rake, overlay and satellite-seat terms, and uses the existing tournament-rake covering index by omitting only zero/null rake amounts from the coalesced sum. Negative amounts remain included. No new index or optimizer setting is needed. Numeric rounding, the greatest of the two overlay records, ticket arrival/departure and cash-fallback rules, satellite/Spin exclusions, oldest-first ordering and limit stay intact. Every byte after the selection, including both refusal branches, alerts, explicit applying branch, reconciliation call, post-payment conservation check and return object, is preserved. There is no new schedule, production payer call, grant, timeout increase or horse exclusion.

Installation guards exact caller/scalar definitions, browser access, owner, immediate valid/ready/live singleton keys and the existing covering index's exact definition and readiness. It preserves the function OID, owner, ACL and settings. The production installer must install once outside the existing DDL refusal boundary and read back definition/catalog/history. Do not invoke the live payer to test this change. Source installation and a natural scheduled result are distinct evidence.

A private socket-only PostgreSQL 17 fixture executes the captured scalar and both complete caller definitions. Only the unchanged payout reconciler dependency uses an explicitly labeled fixture adapter. It compares results, alerts, invocation order, financial fixture rows and logs for applying/non-applying/null flags and limit boundaries. Cases cover null/zero/signed amounts, rounding, overlay duplication, ticket states, cash fallback, malformed metadata and the exact cutoff. Actual service/browser roles use a NOSUPERUSER BYPASSRLS owner; source/key/ACL/index drift, rollback/replay and two concurrent snapshot sessions are tested. A real deferred unique constraint demonstrates the old scalar's duplicate-row error versus a multiplied join, then proves installation refuses that incompatible schema. The baseline mode deliberately rejects the original repeated-query structure; it does not reproduce a provider timeout locally.

The first batch draft still exceeded a 30-second production read-only diagnostic bound. Wallet and rake components each exceeded 12 seconds, while satellite components finished below one second. The final wallet materialization and existing rake-index path completed separately in 1.612s and 2.477s; the combined read completed in 2.985s. These are dated, separately cached/load observations, not a controlled speedup percentage, full scheduled-job verdict or CPU/billing savings. On identical local fixture data containing 12,000 extra healthy events, both selections returned 71 findings (scalar 0.685s, batch 0.060s).

The existing required accounting shard runs the native fixture for every changed input. A source regression also compares the maintained scalar formula with the qualified capture, so later formula changes require renewed batch qualification. Existing financial routes, assertions and historical source-binding records are preserved.
