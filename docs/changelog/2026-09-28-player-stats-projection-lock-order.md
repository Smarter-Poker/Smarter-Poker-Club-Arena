# 2026-09-28: player_stats projection locks in deterministic order

**Incident:** `DatabaseDeadlocksElevated` (severity critical), board [Smarter-Poker/Smarter-Poker-Club-Arena#5070](https://github.com/Smarter-Poker/Smarter-Poker-Club-Arena/issues/5070). 124 `operational_alert_events` rows going back multiple days, never previously investigated despite the severity. `poker_db_deadlocks_total` fired between 12 and ~4006 deadlocks/10min at irregular times through 2026-09-28, most recently 16:06:59Z ("4006 deadlocks in 10 minutes").

**Root cause, read from raw Postgres logs (ClickHouse `postgres_logs`) for the live cycle at 16:05:54Z/16:06:11Z:** one process running `fn_project_hand_side_effects(p_hand_id)` deadlocked against a concurrent process running `fn_credit_agent_commissions_batch(p_items)` - both reported `waits for ShareLock on transaction <xid>; blocked by process <pid>`. This is row-level contention on `public.player_stats`, not the advisory locks each function separately takes (`hand-projection:<table_id>` vs `accounting_cash_hand:<hand_id>`/`accounting_cash_source:<rake_id>` - different keyspaces).

`fn_project_hand_side_effects_after_post_commit_20260908`'s Projection 2 (legacy `player_stats` fold/winnings totals) inserts one row per seated player of the hand in a single multi-row `INSERT ... ON CONFLICT (user_id,club_id) DO UPDATE`, with no `ORDER BY` on its source `seated LEFT JOIN won` query. Postgres does not guarantee any row-lock acquisition order for a multi-row insert without one; the order actually taken follows the join plan (a hash join here), which is not stable across concurrent executions touching an overlapping player set.

`fn_credit_agent_commissions_batch` reaches `fn_process_cash_accounting_source`, which locks the *same* `player_stats` rows one at a time via `public.apply_rakeback_player_stats`, looping `FOR player IN SELECT * FROM accounting_cash_rake_sources WHERE rake_record_id=r.id ORDER BY club_id,player_id LOOP`. Both paths run concurrently for the same hand: the hand-side-effects projection is driven off `hand_projection_outbox` immediately after a hand commits, and the cash-accounting source off the same hand's `rake_record` at the same time. When the two touch an overlapping set of players in different orders, they deadlock; Postgres kills one of the two transactions to break the cycle.

Projections 3 and 4 in the same function already order their own multi-row writes (`ORDER BY f.user_id, f.hand_id`, `ORDER BY 1, 3`) for exactly this reason - Projection 2 was the one left unordered.

**Fix:** `supabase/migrations/20260928172500_player_stats_projection_lock_order.sql` adds `ORDER BY s.uid::uuid` to Projection 2's source SELECT. `v_club` is a single constant value within this statement (one hand, one table, one club), so ordering by `uid` alone is equivalent to ordering by `(club_id, player_id)` for the overlapping club - matching the cash-accounting path's lock order. This changes only which order rows are locked and written within the statement; the `ON CONFLICT DO UPDATE` accumulation arithmetic is untouched, so this is a lock-ordering fix, not a change to any credited amount.

**Hardening:**
- `tests/player-stats-projection-locks-in-deterministic-order.law.test.ts` (registered in `docs/laws.d/`) pins the `ORDER BY s.uid` clause on Projection 2's `player_stats` insert specifically (isolated from the other three projections' inserts), pins that the accumulation arithmetic is unchanged, and pins that Projections 3/4 keep their own existing deterministic order.
- Detection: `DatabaseDeadlocksElevated` already exists as a live alert rule and is the fleet's own detector for a recurrence; 106 of its 124 recorded rows already carry `payload.target_task_id` routing them into this board (18 older rows predate that routing and are a separate, smaller, already-noted gap - not touched by this fix).
- CI: the new law test runs under the existing `npx vitest run tests/` gate in `publish-club-arena.yml` (CLAUDE.md section 8, "never push a red test") on every PR touching this path.

**Verification:** proved by reading the live `pg_get_functiondef` of both functions and the live deadlock log entries before writing the migration; not executed against production (CLAUDE.md 11.5 - this is DDL redefining a function, not a probed money RPC, and changes no data).
