# Interrupted alert-index recovery checks current readers

The oldest production alert's contract lookup index could not be activated because a weekly-close transaction retained an older database snapshot. Recovery run 36933547738 reached PostgreSQL's 600-second limit and left the exact invalid `_ccnew` replacement behind. The recovery admission check incorrectly used the first failed operation's timestamp, excluding a reader that began later but before this attempt.

The follow-up keeps the existing single-migration installer. It checks current database snapshots immediately before each recovery change. Historical timestamps remain provenance. An explicitly identified, invalid temporary replacement can be removed concurrently only after both index identities and definitions match, no other replacement or builder exists, and the migration is still unapplied. The original index is never dropped. Cleanup and rebuilding share the existing bounded recovery budget; a possible write followed by an error remains unknown and is never retried automatically.

The focused isolated PostgreSQL 17 regression passed: a real interrupted reindex left a temporary index; readers newer than the historical timestamp were refused; exact temporary-index cleanup and rebuilding preserved all 2,000 original rows plus an independent concurrent writer. Final index validity and allocation cleanup passed. Eight guard controls and 27 affected installer/routing checks passed. Hosted checks and production installation remain pending. A reader starting after the final admission check remains a race handled by the bounded operation and durable readback.
