# The CSS Beat gate runs in two halves, and the Diamond frames are compared with the base (2026-10-01)

Phase 6 of the mobile graphics programme.

**The CSS Beat gate runs in two halves.** "CSS Beat E2E (multi-table + animations)" is a required check and the critical path of every merge. Run 36886817861 spent 16 minutes in its browser suites, one after another on one build: the beats 3.9 minutes, then the Diamond playfield 7.1 minutes on one software-WebGL worker, then Table Studio 4.5 minutes and the decision gate. The Diamond playfield bundles its own components with esbuild and serves them through `page.route`, so it never needed that build or the shared preview. It now runs as its own job, `diamond-playfield-e2e`, beside `css-beats-e2e` (the beats, Table Studio and the decision gate, still on one shared build, so "one build, three suites" holds). The required name belongs to a new job, `css-beats-gate`, which runs no browser and passes only when both halves passed. It evaluates with `always()`, so a failed or cancelled half fails it instead of skipping it green, and it is admitted exactly when the halves are. The browser time on the critical path falls from about 16 minutes to about 9. `tests/the-css-beat-gate-requires-both-halves.law.test.ts` pins all of it; `tests/ci-tells-the-truth-faster.law.test.ts` and `tests/unit/fixtureNativeCi.test.ts` now read the playfield command from its new job. The ci.yml and fixtureNativeCi pins are restamped in `scripts/qualification/cash-native-hosted.manifest.json` (record `cssBeatGateSplit20261001`) and in the three source bindings that pin fixtureNativeCi, each with its audit entry.

**The Diamond frames are compared with the base.** The informational visual baseline shot every Diamond game at 393 and 1280 wide through each phase, but only for the pull request, so a reviewer saw what it draws and not what it changed. The job now also checks out the commit the pull request merges into, builds its fixture page and shoots it with the pull request's own harness, and `scripts/ci/diamond-visual-diff.mjs` compares the two frame by frame: the share of pixels that moved (past a small per-channel tolerance for rendering noise), a diff image with the moved pixels in red, and a job summary that leads with the frames that changed most and names any frame only one side drew. It decodes and compares in the Chromium the job already installs, so nothing new is added. Every base step may fail: an unbuildable base is reported as "nothing to compare", and the job still never gates a merge.

Tests: `tests/the-css-beat-gate-requires-both-halves.law.test.ts`, `tests/unit/diamondVisualDiff.test.ts` (the pixel rule, the diff image, that the page can run the function as written, pairing, the summary, and the workflow's base steps), plus the updated CI laws above. `python3 scripts/ci/verify-source-bindings.py` and `scripts/ci/test_cash_native_pgcron.py` pass on the new pins.
