# Lightning Phase 13: Rollout, Drain and Rollback

Migration `20261009235505_lightning_phase_13_rollout_drain_and_rollback.sql` (specification Phase 22, the database side). One transaction with `SET LOCAL lock_timeout = '2s'`; three new tables, eight new functions and thirteen asserted substitutions into the bodies PokerIQ-Production carries now (read with `pg_get_functiondef` on 2026-10-09; the harness chain was proven byte-identical to production for all thirteen by md5). Not applied to production by this change. Lightning stays dark: no operator action runs by itself, no new body moves money, and nothing here changes non-Lightning cash play.

The owner rule this phase answers: "Never strand players by simply toggling a flag." A drain is a driven, audited state machine.

## What It Reuses

- **The control gate.** The operations rail's access `control` is platform staff or the club roles owner, co_owner and admin. Its SQL is `fn_ca_is_club_control(club, user)` beside `fn_is_platform_admin()`; the write door uses exactly those, plus service_role. The read gate (`fn_lightning_operator_may`) is unchanged and is the readiness door's.
- **The freeze path.** A manual freeze is the same transition as an automatic one (cluster_mode to `frozen` under the Cluster row lock), the same critical page through `fn_raise_server_financial_alert` keyed `lightning_cluster_frozen:<cluster>` with message `LIGHTNING_CLUSTER_FROZEN`, and the same `cluster_frozen` event (reason and invariant `operator_freeze`). Recovery stays `fn_cash_cluster_unfreeze` only.
- **The reversion path.** The drain ends through `fn_cash_cluster_begin_pending_off` and `fn_cash_cluster_commit_must_move` (Phase 7), so the md5 over every live seat, open cash session and the blind ledger is asserted exactly as before (`LIGHTNING_REVERSION_MOVED_MONEY`).
- **The flag architecture.** The repository's flag table `club_entry_feature_flags` is platform-wide with three fixed keys, so it is not per-Cluster capable. Lightning's gates have always been per-Cluster keys in `ruleset_snapshot -> 'lightning'` read by `fn_lightning_config`, plus `cash_games.lightning_enabled`. That is reused; no flag table is created.

## The Control Door

`fn_lightning_operator_control(p_cluster_id uuid, p_action text, p_reason text, p_args jsonb DEFAULT '{}')`: SECURITY DEFINER, pinned search*path, authenticated and service_role, never anon. Reason required (3 → 2000 characters). `p_args.request_id` (uuid) required; a repeat answers the first answer with `idempotent:true, replayed:true` and writes nothing. Every real change writes one `operator*<action>`row of`cash_cluster_events` with actor, reason, before and after, and the operator's transitions (`fn_lightning_operator_cluster`) and the session trail (`fn_lightning_operator_session_trail`) carry it. Every answer after the Cluster lock is kept in `lightning_operator_request`.

## The Emergency Drain

The existing `draining` cluster_mode and one row of `lightning_cluster_drain` (at most one open per Cluster), driven by `fn_cash_cluster_lightning_drive` through `fn_lightning_drain_advance`; `fn_cash_clusters_tick_all` now drives draining Clusters and any Cluster with an open drain.

1. **Stop new joins** and 2. **stop new formation**: `lightning_enabled` false and cluster_mode `draining` in the request; the pool door, the barrier and `begin_dealing` refuse every mode but lightning.
2. **Let active hands finish**: while a hand is dealing or settling the drain waits, however long. The drain never cuts a dealing hand. Past `drain_timeout_ms` (default 120000, clamp 10000 → 3600000) every instance that never started dealing is abandoned through `fn_lightning_instance_abandon` (`lightning_drain_timeout`); no money moves.
3. **Settle active hands**: recorded when nothing is in flight.
4. **Restore players**, 6. **rebuild MUST-MOVE** and 7. **preserve stacks**: in the same transaction `fn_cash_cluster_begin_pending_off` (which admits a draining Cluster for reason `lightning_drain` only) and `fn_cash_cluster_commit_must_move`: every pool session exits `lightning_drained` to the anchor seat it never left, MUST-MOVE opens at a new epoch with Lightning's halts lifted, and the digest is asserted.
5. **Audit trail**: one `lightning_drain_step` event per step with its counts, the eighth the summary.

From pending_off the reversion in flight finishes (Lightning disabled, it can no longer abort) and its sessions exit `lightning_drained`; from pending_on the conversion aborts through the existing abort (`aborted_pending_on`). A drained Cluster ends in must_move with `lightning_enabled` false and cannot re-convert until an operator enables it. A freeze ends an open drain (`ended_by_frozen`).

## The Flags

`lightning_v1` is `lightning_enabled`; `lightning_shadow_matcher` and `lightning_auto_rebuy` are `lightning_shadow_matcher` and `auto_rebuy_enabled`; `lightning_multi_table` off writes `multi_table_limit` 1 and on restores 4, 3 and 2; `lightning_fast_fold` and `lightning_fold_watch` are two new keys (default true, the behaviour today) the engine's action door enforces. `lightning_pool_health` and `lightning_session_stats` are read-only displays with nothing to protect, and `lightning_repeat_suppression` and `lightning_adaptive_liquidity` are the live matcher itself, which changes only through a matcher version with shadow evidence; all four answer `FLAG_NOT_SUPPORTED` and are reported on. The ten flags with their effective values are in every dashboard row's `flags`, beside the four Phase 12 keys.

## The Readiness Verdict

`fn_lightning_rollout_readiness(p_cluster_id uuid)`, the operator doors' gate, read-only, never anon: `{ok, cluster_id, as_of, verdict, reasons:[{code, severity, detail}], evidence}`. The verdict is `no_go` with any blocking reason (`MIGRATIONS_MISSING`, `MIGRATION_LEDGER_UNREADABLE`, `INVARIANT_FAILED`, `CLUSTER_FROZEN`, `CLUSTER_BUSY`, `CLUSTER_NOT_READY`, `GAME_DISABLED`, `NOT_A_MUST_MOVE_GAME`, `OPEN_ALERTS`, `INTEGRITY_HIGH_SIGNALS_OPEN`, `LATENCY_ABOVE_CEILING`, `MATCHER_VERSION_INVALID`, `AA_CALIBRATION_BIAS`, `WORKER_OFF`), else `insufficient_evidence` with an evidence reason (`NO_AA_CALIBRATION`, `NO_LATENCY_EVIDENCE`, `WORKER_SHADOW_ONLY`), else `go`. Evidence: every Lightning migration recorded in `supabase_migrations.schema_migrations`; the structural invariants the live proofs pin, re-derived in SQL (the seven-tables census, the anti-manipulation pin, Law 10.5 over every `fn_lightning_` body, no anon door); the Cluster's state; open pages and high-severity signals; the A/A calibration and the candidate from the Cluster's shadow comparisons or else the estate's; latency against the alert ceilings; the matcher and the worker mode. The live proofs themselves are evaluated by `bin/proofs.sh`; shipping every file's text into the database to evaluate them in SQL was judged impractical.

## Laws

- Law 10.5: nothing reads `is_horse` or `horse_id`; humans and horses are paused, drained, released and re-entered alike, and the harness proves both are among them.
- No money moves on a mode transition: the drain ends through the asserted reversion; pause, joins, flags and matcher actions write no seat, cash session or blind ledger row.
- No matchmaking manipulation: legality reads the joins key through the configuration it already read and calls no operator function; the anti-manipulation pin is restated.
- Hidden information: no answer carries a card; the readiness door answers through `fn_lightning_operator_redact`.
