# A new club can be retired while its opening board is still opening

A new club's twelve-game welcome board (four heads-up SNGs, eight 1-chip Spins) is opened by the engine a few games per tick, so for the first one to three minutes it holds between one and eleven of the twelve. Both welcome-package authorities recognised the board only when it held none or all twelve, so an owner who opened Retire Club in that window was told the club was not an unused welcome club, and the Create Club production certificate failed the same way (run 38151574882).

Migration `20261011193040` changes only the board-identity rule in `fn_get_club_welcome_package_reset_impact` and `fn_unwind_unused_first_club_welcome_package`: any number of the twelve exact games counts, while a duplicate name (an owner-made look-alike) is still refused. Every other proof - no seat, session, waitlist, registration, hand or executing command, untouched BBJ and Spin seeds, the global settlement lane - is unchanged. It is an exact-fragment rewrite with preimage, round-trip, catalogue-attribute and postimage checks, and replay is a no-op. `scripts/ci/test-club-welcome-package.py` gains four cases (partly opened board can reset; it unwinds every opened game; a duplicate is still refused; nothing leaks); without the migration the first fails with `false|package_economics_not_pristine|5`, with it all 175 cases pass.

Certificate cleanup also waits out a scheduled maintenance break when the break is reported as a raised `PLATFORM_FROZEN` error rather than a `platform_is_frozen` answer. Runs 38148991448 and 38161401967 failed red that way during the break; the same fixtures were retired untouched by a later run. Both the reserved-account sweep and the fixture-club retirement now use the existing thaw wait with the existing two-freeze bound, and refusals that are not the freeze are never waited on.
