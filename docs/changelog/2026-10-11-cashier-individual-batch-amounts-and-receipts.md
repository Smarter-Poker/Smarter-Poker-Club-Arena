# Cashier Individual Batch Amounts And Receipts

Phase 5 of the seven-phase cashier programme. A selected batch can assign a different chip or ticket value to each recipient. The confirmation total sums exact cents, names the actual funding wallet, and explains invalid amounts, unverified access and insufficient funding before submission. The entire amount plan is validated before the first bounded request. Amount inputs lock while acknowledgements are pending.

Each recipient owns an immutable saved amount, destination and retry key. Existing uniform-amount journals remain compatible. Reload recovery checks original receipts first, excludes confirmed recipients from retry, and retains their original amounts in the combined receipt. Editing an individual amount starts a separate intent without deleting the unresolved one. A recovered single recipient's input and wallet context show the exact preserved intent, even when their role changed afterward.

Batch receipts show exact recipient values, wallet destinations, references, and distinct confirmed, refused, unconfirmed or unsubmitted outcomes. Only confirmed values contribute to the confirmed total. Missing, duplicate, malformed or mismatched acknowledgements remain unconfirmed. Operators can copy the receipt; the existing authoritative history and original receipt reader remain the durable source.

Regression protection covers real mounted Trade and existing wallet recovery, exact amount validation, immutable journals, partial outcomes, lost responses, ticket keys, edits, input locking and original destinations. Native PostgreSQL qualification executes the shipped batch wrapper against isolated authority and money-movement witnesses, proving different values, identical replay, per-recipient exact-intent refusal, invalid precision and anonymous refusal. Maintained production browser checks preview different values and ticket funding without submitting real money. No database migration, engine replacement, financial replay or scheduled repair was introduced.
