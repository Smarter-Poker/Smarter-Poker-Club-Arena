# Cashier Large Roster And Receipt Performance

Cashier searches now score each authorized member once before sorting. Match quality, self-first results, selected sort, role grouping, assigned filters, server scope and the complete searchable roster are preserved. Existing progressive rendering still shows 25 rows initially and loads 25 more per click. Batch receipt updates use indexed recipients and linear replacement sets; recovery names use the current roster index. Exact individual amounts, original references, unknown outcomes, same-batch identity and the 25-recipient server boundary are unchanged.

Independent scaling qualification reproduced the original repeated work: a 10,000-member broad search read names 249,712 times; the final path reads 10,000 times. Merging 5,000 previous receipts with 2,500 retry rows read replacement IDs 9,376,250 times; the final path reads 2,500 times. These are deterministic operation counts, not a claimed browser latency improvement. Search results and ordering are compared with the original predicate/ranking across empty, broad, handle, number, readable role and nonmatching queries. Exact receipt values, references, prior confirmations, replacement order and input immutability remain asserted.

The actual mounted Cashier loads all 2,000 members over four full pages and a terminating empty page, initially renders only 25, finds the final member by number, opens their composer and submits only their exact 0.20 through the synthetic batch fixture. The real component and global fonts/styles were also checked at 375, 393 and 1440 pixels with a 2,000-member isolated roster; Load More grows 25 to 50, search finds the final member and native selection opens the correct preview without document overflow. Financial fault tests use isolated PostgreSQL and local fixtures; production checks preview only. No migration, engine replacement, new dependency, scheduling mechanism or visual redesign is introduced.

Before Phase 6 implementation, Phase 5 was freshly reverified with 116 connected tests, 149 isolated database cases, production function hashes and permissions, both published build identities, scoped hosted Cashier/database/Statements successes, and actual send/ticket individual-amount previews. Publication and final protected qualification are recorded in the existing task checkpoint after completion.
