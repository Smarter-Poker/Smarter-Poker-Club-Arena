# Retire qualified fact cards with one original update

The original per-hand compactor issued one card UPDATE per qualified hand. Each statement fired all three maintained rollup UPDATE triggers, whose zero-delta calculations correctly preserved earnings and counts. A 250-hand batch therefore invoked those real rollup functions 750 times.

This successor keeps every per-hand advisory lock, disposal qualifier, accepted-stat capsule, certificate insertion, retired-card row guard and authorization unchanged. It collects the qualified hand identities and runs the original card-only UPDATE once, reducing the same batch to three statement-trigger invocations. An empty/replayed batch performs no UPDATE. All work remains inside the existing retention transaction and its original bounded caller; no scheduler, repair loop, financial adjustment or new cleanup job is added.

The existing connected native owner now qualifies this transition after the actual adaptive, facts, review, snapshot and lifetime source. It exercises 250 distinct hand identities and varied derived values with the actual statement-trigger bodies: old 750 versus new three invocations; exact noncard facts, all three rollups and accepted capsules; protected-hand exclusion; rollback; shared admission concurrency; duplicate no-op; access and migration replay refusal. The qualified helper keeps PostgreSQL ownership, postgres-only execution, SECURITY DEFINER and its pinned search path.

This proves less statement churn, not a production capacity increase. The isolated warm 250-hand fixture took approximately 0.143 seconds before and 0.150 seconds after, so it demonstrated no runtime improvement. Production ingestion and retention throughput must still be compared after installation; neither EXPLAIN estimates nor this small fixture prove that the eight-day backlog can keep up. The production candidate SELECT itself returned 250 candidates in approximately 0.212 seconds during the bounded read-only diagnosis and was not the main measured batch duration.
