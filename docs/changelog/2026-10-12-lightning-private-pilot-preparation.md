# Lightning Private Pilot Preparation

The installed shadow window defaults to 300,000ms. Thirty comparison windows
need 150 minutes, exceeding Stage 1's one-hour budget. Game creation ignores
arbitrary Lightning overrides, and the operator door had no numeric setter.

The forward migration adds `set_shadow_window` to the original operator door.
It requires an integer from 60,000 through 3,600,000ms and a drained MUST-MOVE
Cluster with its worker off. Existing authorization, row locking, reason,
request identity, audit event and money invariants remain authoritative. It
changes no production Cluster during installation. The real PostgreSQL harness
reproduces the missing operation, then checks permissions, invalid types/bounds,
live-pool and running-worker refusal, real drain, persisted settings, one event
under replay, identical money/stacks and migration reapplication. The original
20 sections and predecessor proofs execute before this new qualification.

A dispatch-only setup workflow uses the configured verified service account to
create one durable private standalone pilot club with approval required and one
private six-seat NLH MUST-MOVE game. Club creation retains a fixed request ID;
unknown game acknowledgements recover from durable identity before another
creation. The script rejects a different service identity or an already active
pilot. It sets only the pilot's one-minute calibration window through the
operator door, keeps Lightning and its worker off, and records identifiers.
It creates no player identities, financial fixtures, hands or evidence rows.
It cannot enable or certify a release and has no schedule or repair loop.

The owner deferred seven/fourteen-day observations while functional preparation
continues. Outsider access, participants and actual Lightning hand proof remain
separate from empty-pilot preparation. Public launch remains NO_GO.
