# Roster rows share funded hand counts and live source events

The member list counted hands from the physical-club totals while member records and statistics count them under the immutable funding club. The shared roster reader now sums the same cutoff-qualified daily projection. Fees still come from their cash and tournament ledgers; wallet sources, row permissions, filtering, sorting and exports keep their existing contracts.

Private `club-roster:<club UUID>` broadcasts use `record_changed` with an empty payload. Admission matches the roster reader's exact-club active membership, platform administration and union-overseer rules. Financial and note access remains a server-side row decision. Existing member-record producers relay identity, membership, seats, facts, agents, fees and transaction changes; explicit old/new clubs include membership removal. Union parents receive invalidation without widening their row scope. A transaction-local deduplication value emits at most one roster event per affected club per transaction and rolls back with the source transaction.

Membership activity was already a source of the roster's Last Active value but was absent from the member record and its source trigger. Both readers now use the greatest profile login, profile heartbeat and membership activity timestamp; the existing membership trigger includes that source column.

The roster also used profile display names where member records use the canonical arena name. Two actual alias fallbacks and 1,800 display-name fields disagreed in the finite production comparison. Roster alias, display and upline fallbacks now use the same maintained arena resolver, including its real-name privacy rule. Member player/promo wallet columns invalidate the authoritative roster window as well as the existing wallet-value channel, so wallet sorting cannot retain an obsolete row order.

The required Data Console native check retains a before/after reproduction with two independent clubs: twelve hands funded by one club but physically filed in the other. It verifies corrected counts, cutoff generations, unchanged fees/wallets and identity-only redaction, Last Active parity, actual source-trigger event relay, private provider-probe authorization, outsider/suspended/administrator/overseer cases, empty payloads, union fanout, transaction deduplication and rollback. The existing attribution, concurrent capture and reader/writer lock fixtures remain enforced. Production acceptance uses one materialized roster read per club plus independent aggregate sources; it does not mutate production players to prove updates.
