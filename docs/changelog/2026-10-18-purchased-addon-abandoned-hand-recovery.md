# A purchased add-on does not strand an abandoned hand

The Oct18 restart incident left twelve permits reserved by dead generation8dbac0bd in eventf498902d. Two hands had cards but no snapshot. Five chairs held exactly their last committed stack plus the event's10000-chip purchased add-on; every playing registration matched its chair. The existing snapshotless misdeal branch refused those valid purchases and prevented the whole generation from receiving a terminal disposition. The saved-snapshot branch already supports this same add-on proof.

The existing recovery transaction now accepts only the exact positive event add-on for the same playing registration marked add_on=true. Every other guard remains byte-identical: current lease, commit/history/private state, retained submission, card membership, roster and stack equality, receipt identity and hand fencing. This writes no player balance, registration, wallet or ledger and adds no repair loop. The installer asserts the exact production preimage, owner, ACLs, security and search path, and refuses replay or drift.

Native PostgreSQL17 runs the complete installed function before and after the actual migration. The observed shape fails before and passes after; unpurchased, wrong/double/zero add-on, roster mismatch, unknown card, retained submission, accepted hand, live generation and browser identity still refuse. Identical receipt replay is idempotent, the old permit is fenced, and chairs, registrations and the current lease remain exactly unchanged. The same qualification runs in the existing required F06 accounting shard. Source contracts pin the single-clause delta and full function hashes. Production installation and affected-event recovery are recorded separately in the task checkpoint.
