# A Restarted Lightning Feeder Counts Its Player's Completed Hand

A physical anchor booted under its cluster's dealing halt never enters the ordinary dealing loop. Its `dealtInUserIds` therefore stays empty while the same original cash occupancy completes real Lightning hands. The existing `/sitout` pool-to-anchor route reached the ordinary one-hand gate and could refuse such a player. The actual earlier production witness omitted its refusal code, so this reachable defect is not asserted to be that response's proven cause.

The existing route first preserves the ordinary engine decision. Only its explicit no-hand refusal on an authenticated open Lightning pool asks for completed participation. The read pins original cash identity and current pool slot/player, requires a settled hand, and rereads the open anchor after awaits. The engine accepts that proof only for its same current occupancy on a halted cluster. It does not seed button eligibility or mark a newly joined player as having played. Ordinary cash, no-hand refusal and return semantics remain intact. No migration, timer or polling is introduced.

Regression drives the real engine method on a restarted feeder (the valid completed-hand case fails on the original source), the authenticated HTTP handler, and the maintained Supabase adapter including no-hand, unknown-read, original cash and replaced-occupancy fences.

Real-time law: existing PLAYER_SAT_OUT / PLAYER_SAT_BACK discrete event and persisted Sit Out publication remain the state-change owners; no snapshot diff.
