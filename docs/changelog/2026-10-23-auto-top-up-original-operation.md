# Auto Top Up Retains Its Original Operation

Ordinary cash Auto Top Up retained the request ID while recalculating its amount from a changed wallet balance. The database binds both values, so the lost-response retry could become an invalid payload. The client now retains the original amount, rejects invalid funding inputs and mismatched table/player identity, fences replies after scope changes or unmount, includes the table maximum in its trigger dependencies, and permits one acknowledged automatic purchase per hand.

A focused real-engine test also reproduced stack 10 → 20 → 30 from two identical top-ups of 10, although the database's repeated response represents one debit. Funding requests now join duplicates and serialize each player's commands. The engine reads the original immutable operation before cap/mutation, recovers current absolute seat and pending truth, and resolves lost acknowledgements from that same operation. It does not replace a running hand's stack with the opening stack on disk. Unproven direct outcomes fence the affected table generation instead of permitting another deal from an unproven stack. No global restart, watcher, repair timer or new money writer is introduced.

Both chip and Diamond readback functions are service-only and read-only. Migration 20261023182011 must be installed before the engine candidate activates. Diamond duplicate intents return their existing amount before counting their own reservation against headroom. The client preserves replay/unknown status through HTTP, accounts once per operation, and reads absolute wallet balance on recovery instead of subtracting the debit again.

Regression protection includes focused client/engine tests, before-fix engine failure evidence and a private PostgreSQL qualification of the actual readback functions and role/identity boundaries. The native qualification runs directly in required accounting CI. Source checks, protected merge, installed migration, served component identity and affected live proof remain separate; see CHECKPOINT-auto-top-up.md for actual delivery state. No live chips are spent for a test.

Session accounting now restores the recorded chip baseline or Diamond custody recap at entry, reconnect and committed top-up events. This removes acknowledgement/snapshot and wallet/refund ordering double-counts. Lightning resolves its original anchor seat. Queued Diamond intents emit a private terminal receipt and retain their original payload through transport failures; maintenance/lifecycle fences prevent late funding/reflection. Session stack and peaks come from actual snapshots.
