# Lightning top-ups retain their original uncharged intent

A Lightning anchor's physical controller has no live hand controller while a virtual hand owns its chips. The ordinary Add Chips path therefore tried to credit a live anchor immediately; the database correctly refused it. An early folder can still have an older outstanding hand, so finishing their current display hand is insufficient permission to fund the anchor.

The new private intent records the original amount, operation key, pool session and occupancy without charging. The final outstanding hand's existing terminal transition calls the unchanged platform add-on transaction, caps the actual amount to configured headroom and records the terminal receipt. Abandonment, exit, insufficient funds and maintenance terminate the intent without a charge. Matcher planning and actual formation revalidate pending intents under the original anchor locks. No anchor, reservation, funding, freeze or original receipt guard is relaxed.

Manual Add Chips and opted-in human and horse callers share this request. Horse requests retain the existing seat flag, PLO5 refill policy and bankroll allowance; cluster auto-rebuy settings are unchanged. Completion uses the existing transaction event subscription. Own reconnect and completion reads return current wallet and cumulative funding, pending receipts and at most 32 latest completed receipts, with durable historical requests retained. Client accounting uses canonical totals rather than requested amounts or receipt deltas. Historical or reordered completion messages cannot restore an older stack.

The client can publish while the old engine serves: only a current authenticated own-room snapshot advertising `lightning_original_top_up: true` enables automatic intent requests during an overlapping hand. Missing capability retains the old between-hands condition. Disconnect and room changes clear capability. Install the qualified migration before activating the new engine; a missing RPC fails visibly and never falls back to an unsafe direct credit.

The only source dependency reused from open PR #7835 is the additive `SessionStatsService.restoreFunding` method for canonical cumulative funding. This change does not replace that owner's ordinary funded-pending-addon receipt work or use PR #8016's polling approach.

Qualification runs against isolated PostgreSQL 17 with exact captured platform funding, ledger, baseline, custody, idempotency, anchor-guard and terminal function definitions. It invokes actual formation and legality functions and races an original request against formation. This qualifies the affected transaction boundary, not an entire platform settlement or production game. Local source qualification, protected integration, database installation, client publication, certified engine activation and natural live behavior remain separate delivery evidence.
