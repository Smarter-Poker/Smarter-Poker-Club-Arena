# A stylesheet failure never reloads a page that is already live (2026-10-26)

Production post-deploy run 40260290873 (WebKit as an iPhone) failed the mobile lobby check the same way run 40242809027 did: "Navigation to /hub/club-arena/ is interrupted by another navigation to /clubs/kings-club?\_cb=...". #8101 (ask the server about a failed stylesheet) and #8100 (check the live build after the grace) were both in that release. The trace shows the remaining gap: leaving the Kings Club lobby cancelled its stylesheet preloads, and WebKit cancelled the stylesheet probe too ("due to access control checks"), so the probe answered `unknown`. That path, and a reinstated stylesheet whose own load fails, still replaced the document without asking which build production serves. iOS Safari sends no beforeunload, so `documentIsNavigatingAway()` never knew, and the slow navigation was cut off by a reload of the page being left.

`recoverFailedStylesheet` now asks production (`readLiveBuild`: `this` / `other` / `unknown`) before a stylesheet failure replaces the document. If this document is the live build, a reload would fetch the same files, so the stylesheet is put back (once) and nothing reloads. If a newer build is live, recovery runs as before. If nothing can be read, which is what a departure looks like from inside it, recovery asks again after each grace for up to `CURRENT_BUILD_PATIENCE_MS`. A 404 for the stylesheet still recovers at once. `liveBuildIsThisDocument` keeps its contract on top of `readLiveBuild`.

Two tests that pinned the blind reload were updated deliberately in the same commit, and four new cases in `tests/chunk-load-recovery.test.ts` fail before and pass after.
