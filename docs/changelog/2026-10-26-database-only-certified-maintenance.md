The Lightning mode-dwell migration remains absent after its containing engine activated. The existing seal refuses a recovery reservation for an already-serving engine, so an installer-only continuation cannot create its own certified window.

The existing staging provider now offers an explicit `request_database_break` option for a reviewed database window. It uses the same seal and rolling-hour reservation journal, takes the existing engine mutation lock for the complete operation, and refuses a pending, finalizing or awaiting engine owner. It binds the protected control source, actual immutable serving image, high-water ancestry and exact migration bytes without changing the sealed image, desired revision or generation.

The serving controller still owns the two-minute notice, hand-boundary drain, five-minute freeze and v3 thaw. Installation requires the original drained certificate with 285 seconds remaining and then uses the unchanged SQL installer, its 150-second admission reserve, one-second locks, five-second statements, eight-second transaction budget and 100-second commit reserve. A lost request acknowledgement is observed using the same durable timestamp; it is never resent. The same serving instance and its own completed resume waves must be proven before the host lock is released with a successful receipt. No restart, forced thaw, image cutover, recurring worker or second publisher is introduced.

The read-only preflight rejects unknown history and static SQL before reserving a window, and an already-installed file requests no maintenance. Native qualification covers real Git ancestry, atomic reservation and shared-hour refusal, exact replay, immutable-image refusal, high-water rollback, certificate boundaries, stale thaw witnesses and lost acknowledgements. Publication and actual host adoption, installation history, all four database proofs and final thaw remain separate completion gates.
