# Explicit private V56 replay in the maintained qualification workflow

The manual `v56-private-replay` operation joins authenticated private journal acquisition to the existing Phase 15 offline CLI. Its metadata-only `replay_request` is `{ "version": 1, "sourceRelease": "<recorded protected 40-hex revision>", "cases": [{ "handKey": "<64-hex original hand hash>", "actionOrdinal": 3 }] }`. There must be one to six distinct full-list hand/action coordinates. An optional `decisionSha256` narrows the privately derived unique decision; it cannot substitute for accepted-action binding. The provider adds its own run ID.

The existing pinned reader supplies original records privately. The selector reconciles the complete original hand and uses the maintained accepted-hand binder's returned ordinal. It never filters the action list before numbering. Source, physical Git checkout, Node/V8/architecture and current privileged controls must agree. The recorded source must already contain this operation and the Phase 15 `--v56-cases` implementation; older engine captures cannot be relabeled. This change depends on that CLI's protected delivery and does not establish natural replay proof.

The transport retains legacy SHA-only headers and adds separately labeled container and actual engine-instance identities from the bounded native health reader. Container ID is never treated as process identity. Acquisition and offline execution are separated: the job removes its SSH key before invoking the fresh scrubbed/network-refused Phase 15 children, and provisions the same canonical reader identity only after those children exit for the final source/instance check. Raw journal material stays in memory and owner-only temporary files outside the checkout, is never logged or uploaded, and is removed by the owning job. The only artifact is the closed sanitized replay receipt. Missing retained inputs, runtime/stores, source/control bytes or identity evidence remains unavailable.

Qualification and signer-identity job bodies retain their existing authority boundaries. The replay jobs receive no signing key or database credentials, issue no catalog, and always report `qualified=false` and `activationAllowed=false`. No schedule, publisher, production policy execution, store-acquisition route or release operation is introduced. These orchestration/transport controls do not enter the P10–13 reference-policy closures; they do change the P14 current-control fingerprint.
