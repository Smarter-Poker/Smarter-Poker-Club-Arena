# Lightning terminal transitions retain private top-up authority

Production PostgreSQL logs on October 27 and October 28 show valid Lightning abandonment, begin-dealing refusal and matcher calls failing with permission denied for lightning_top_up_intents. The terminal instance trigger was SECURITY INVOKER but reads that deliberately private table. The service role can update the public instance through the maintained doors but cannot select private intents, so the trigger rolled the entire transition back even when no intent was pending.

A guarded migration changes only the existing trigger function to SECURITY DEFINER under its pinned postgres owner and existing fixed search path. Its complete body and execution ACL remain unchanged. The private table stays denied to service and browser roles; the existing private finisher execution contract stays unchanged. Reservation release, blind credit/stamps, original funding, cancellation, maintenance checks and idempotency continue through their original statements.

The existing PostgreSQL fixture now loads the exact current production trigger and reproduces the permission failure as service_role, with the original transition and money unchanged. It then verifies completion funds once, terminal replay does not charge twice, abandonment cancels without charging, an empty-intent abandonment succeeds, browser transition denial, unchanged private permissions and exact body/ACL preservation. All original top-up checks remain. Its existing directly triggered workflow includes the new migration and captured source fixture. Protected merge, exact installation and natural production transition evidence remain required; no game-engine replacement is needed.
