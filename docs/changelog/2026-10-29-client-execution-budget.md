# Bound client qualification to the available hosted compute

The warm-runner UI delivery received every client/control runner in two seconds, but the unit shards still capped four-CPU VMs at two workers and equal-count browser partitioning clustered sixteen expensive occupied-portrait cases in one shard. That browser job took 725 seconds, including 406 seconds of actual cases. Runner assignment alone does not meet the delivery-speed goal.

Request four client Vitest workers, bounded by the actual available CPU budget, and divide the same CSS browser inventory into ten disjoint hosted shards. Keep every case, assertion, retry policy, product/test deadline, required aggregate, financial/Studio/enrollment gate and production transaction. Independent browser gates still execute exactly once on shards 1, 2 and 5. Unknown dependency readers and financial changes retain the existing full qualification path.

The change requires its own exact-head checks and live delivery measurement. No SQL, engine activation, financial rule, custom runner or release watcher is introduced.

The hosted four-worker qualification exposed a one-shot member refresh test readiness race. Flush initial passive effects before delivering its event; retain every permission, call-count, stale-record and no-toast assertion. The isolated original case passed locally, so scheduling is the diagnosed boundary rather than a reproduced production defect.

Actual hosted and list evidence showed equal-count sharding still clustered all sixteen expensive occupied-portrait cases together. Split that exact title group from its complement before ten-way sharding; both partitions retain the same assertions, projects, retry and deadline. Per-job reports remain independent. Studio, financial decisions and enrollment execute once in the general partition.
