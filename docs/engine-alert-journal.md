# Durable engine alert delivery

Engine observations are checkpoints on the host directory `/var/lib/club-arena/engine-alerts`. The same directory is mounted at the same path in the engine. `ENGINE_ALERT_JOURNAL_HOST_DIR` may select a different dedicated host directory in the canonical launcher; the container path stays fixed. Checkpoints contain active fingerprints and a FIFO of immutable failure and recovery events. A recurrence receives a new episode UUID even when its timestamp matches an earlier occurrence. Page priority follows both the failure and its recovery into Codex; engine operational alerts no longer mirror to phones. Customer/account notification code is independent.

Every transition is persisted using a private temporary file, file fsync, atomic rename and directory fsync before HTTP delivery. A checkpoint includes a SHA-256 checksum and validated schema. A failed read or write never invents an empty queue. New observations remain in process memory until the store is writable, with an explicit error; they cannot survive a process loss before persistence. Queued observations keep the actual failure/recovery observation timestamps even if reading storage is temporarily impossible. Missing HTTP configuration and unavailable receivers leave persisted events pending. Startup and a five-second retry timer resume the queue without needing another producer call. There is at most one eight-second HTTP attempt in flight; network work does not hold the checkpoint serialization lock or delay subsequent observations from being persisted.

The receiver must support immutable `labels.engine_alert_event_id` UUIDs. Its success reply is `{ok:true, recorded:1, db:"ok", destination:"codex", receipts:[{id:<positive safe integer>, event_id:<matching UUID>}]}`. WorldHub writes the original event and its delivery receipt transactionally. Replaying an unchanged event returns that same receipt; changing payload under that UUID is rejected. The engine removes a pending event only after receiving its matching receipt and persisting the new checkpoint. Lost responses and failed acknowledgment checkpoints therefore replay the same event rather than create another incident. An older receiver without this contract leaves the event pending. Deploy the compatible receiver before this engine release.

The file store has a single-writer deployment contract. Every supported deploy and recovery path uses the canonical `engine-up.sh` lock, then waits for the old named container to stop, removes it, and starts its replacement under the same Docker name while retaining the lock. The journal is accessed only by that engine process; never start a sidecar, second engine, or ad hoc repair writer against the live directory. Docker name uniqueness also prevents a replacement from starting if removal fails. Normal restart exits the old process before starting the next. The release seal reads the immutable image capability label and refuses a journal-capable image without the correct writable host mount and container environment. Older sealed images remain eligible for rollback, and their rollback does not delete this directory.

Shutdown settles checkpoint work with a bounded one-second wait only after gameplay ownership has been released. It does not wait for receiver availability or change funded-state shutdown ordering. If storage is corrupt, its exact bytes are retained at the original path and in `journal.corrupt.<sha256>.json`; delivery pauses instead of discarding evidence. Recovery requires stopping the writer through the ordinary engine lifecycle, preserving the corrupt evidence, reconstructing a validated checkpoint from the preserved event history and receiver receipts, and restoring it before the normal restart. Do not clear the checkpoint as an error fallback. HTTP failures, storage errors, and logging failures cannot throw into gameplay.

The existing `/health` response exposes `alertDelivery`: loaded state, pending count and oldest observation time, last HTTP attempt/acknowledgment times, active count, unpersisted observations, dirty checkpoint state and error. It includes no event payloads and does not change dealer liveness or restart policy. A healthy fleet pulse submits recovery even in a new process with no local firing counter; the durable journal handles deduplication. Unknown pulse values never fabricate recovery.

Regression coverage includes an actual child process exit/reload, failure/recovery/recurrence ordering during an in-flight send, unavailable storage, acknowledgment checkpoint failure, receiver timeouts and false successful replies, invalid UUID/priority quarantine, shutdown ordering, and the canonical mount/seal/single-writer release contract.
