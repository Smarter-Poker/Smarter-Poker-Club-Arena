# Diamond Phase 11, line 4: the chip estate still passes

Phase 11 line 4 of the Diamond Arena build programme: "Exercise shared chip-club
regression suite without spending real user funds." The Diamond Arena changed
shared code in Phases 2 to 10 (the engine's hand, seat and settlement paths,
shared SQL doors edited by asserted substitution, the lobby, the table page, the
wallet and statements). This file records every chip regression suite that
exercises that shared code, what each one said about `main` on 2026-09-30, the
production suite that is red and why, the audit of which identities the
production suites use, the local runs, what was fixed, what remains and a
verdict.

Written 2026-09-30 between 11:20 and 12:40 UTC against `main` at `52addc2502`
(then `71848aae99`, a non-Diamond tournament clock fix, landed). Everything read
from production was passive: the engine `/health` JSON (cache-busted), the
Supabase Postgres log stream, read-only catalogue selects and one read of the
Diamond identity inside a `READ ONLY` transaction. No load, no write, no
account.

**Verdict: line 4 is ticked.** Every CI chip suite is green on `main` at `52addc2502`,
a million-hand chip-conservation soak and the engine simulator pass locally, the
production suite runs only as reserved test identities that cannot move a real
balance, and the one failure caused by Diamond code on a shared surface is
fixed here (#5643). The production workflow stays red for reasons that are not Diamond:
three real chip-side production defects and two properties of the
certification harness, each named below with its evidence and owner.

about 9,900 (25-26 September), 12,700 (26-27), 12,700 (27-28), 43,000 (28-29) and

already in the engine releases that served the quiet days before the jump. This

## 5. What was fixed

In [#5643](https://github.com/Smarter-Poker/Smarter-Poker-Club-Arena/pull/5643), the mobile lobby spec now settles the Diamond Spins offer before it measures the
lobby. `tests/e2e/support/diamondInvitationOffer.ts` starts listening for
`fn_diamond_games_entry` before the spec navigates. Once the lobby is up it reads
the answer with `DiamondBustPrompt`'s own rule (a successful entry, `bust_prompt`,
zero member chips, at least 25 Diamonds). Not offered: nothing to do. Offered:
wait, with `page.evaluate` and not an action, until the invitation has opened or
the handler has already declined it; then retire the handler and take the real
Not Now through `declineDiamondInvitationIfShown` with its whole budget. Nothing
is forced, skipped or seeded. A layer covering the invitation is still named, an
invitation that will not close still fails with its own error, and a lobby that
never asks keeps the old handler. `production-mobile-lobby-chrome.spec.ts` calls
it from `openLobby`, so all three tests in the file get it.
`tests/unit/diamondInvitationOffer.test.ts` (client unit suite) pins the reading
to the component's eligibility clause, dialog label, dismissal key and Not Now
plate, pins the service's RPC name, and pins the order inside `openLobby`.

This is test code only: no migration, no product change. It takes effect in
production at the first publish after merge, because the post-deploy workflow
takes page specs from the commit production is serving.
