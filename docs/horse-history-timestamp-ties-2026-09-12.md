# Restart replay retains timestamp ties

The existing HorseMind restart reader paged descending by `created_at` alone. When a page ended within a group sharing that timestamp, its next strict timestamp filter skipped every remaining hand in the group. The reader now selects the hand UUID, orders by timestamp and UUID, and advances with the matching two-part filter. PostgreSQL's original microseconds are retained; millisecond parsing cannot collapse the cursor or reject a correctly ordered page.

The original 72-hour lookback and 12,000-hand ceiling remain. A fixed upper time bound excludes future/newer rows from the current pass. The optional flush cutoff is compared by actual time, retaining valid sub-millisecond text and clamping old, future or malformed values to the bounded lookback. The whole page is validated before observation: malformed identities, out-of-window rows, oversized pages, repeats and reversed ordering are rejected. A later failed page preserves earlier validated history, and an unusable action payload remains isolated to its hand. Existing worker and HorseMind ownership are retained.

Original source `cbd522d149d2c6a71612164cf0992b61a61fb6a9` passed compilation and 38 focused tests. Integrated source `0e8160982505b81bb84df9ce3facbf4abdb66e20` on protected main `150c017886e9e59057e68ecff85d55f0d4f0048b` passed compilation and the full server suite: 11,221 tests in 766 passed files, with 145 existing skipped tests and one skipped file. The previous source-law test now pins both cursor components while retaining the newest-first, reverse-replay and bounded-page assertions.

An isolated PostgreSQL 17.11 fixture ran the actual frozen old and new replay functions through a parameterized native SQL transport adapter. With 2,500 equal-timestamp rows and one row one microsecond earlier, the old reader returned 1,001; the corrected reader returned all 2,501 exactly once in the independently queried order. With 13,001 rows, the corrected reader returned exactly the newest 12,000; the old reader again returned only 1,001. The fixture database was stopped and its owned directory removed. No production data, account, chips or schema was modified.

The native harness's initial module-URL error and independent-query alias-ordering mistake were corrected and their negative logs retained. The final SQL oracle explicitly orders the real history UUID, not its selected action-ID alias. The corrected production file SHA-256 is `f1c19da0c8b9e28540c9a80bc65a678e2a1282da32d855768b60e1f1087ba1d4`.

This proves the replay paging repair and native PostgreSQL ordering. It does not exercise a native PostgREST gateway, create a repeatable database snapshot across pages, solve late-commit visibility or prove persistent model deduplication. Those source-window and durable-pipeline requirements remain open for Phase 14. Protected publication and the served engine identity remain separate gates.
