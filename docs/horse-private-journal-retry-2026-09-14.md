# Bounded private Horse journal recovery

The actual Horse journal publisher now retries a lost disk acknowledgement, unexpected writer exit/error, failed worker transport or transient SQLite lock while keeping the same immutable event IDs, producer UUID, sequences and complete-record digests. A replacement can replay an already committed event and obtain the existing exact acknowledgement. It cannot create a second event from the same captured decision or overwrite conflicting bytes.

Recovery is limited to two replacement workers per publisher lifetime, with250ms and1000ms delays. The existing64-record/4MiB queue remains in memory throughout recovery and continues to enforce its capacity. The writer must confirm termination within one second before any replacement starts. Failed, rejected or unconfirmed termination ends recovery and records uncertainty. A retired worker's late acknowledgement, error or exit cannot affect its replacement; callbacks are fenced by worker identity and generation. A factory cannot reuse a retired writer.

The actual private writer classifies only native SQLite BUSY/LOCKED numeric result codes, including their extended codes, as retryable. These codes describe concurrent connection or locking conflicts in [SQLite's result-code documentation](https://www.sqlite.org/rescode.html). Schema, corruption, capacity/full-disk, read-only, permission and unknown errors remain unavailable. Private error strings, paths, cards and identifiers do not enter the worker's failure response or finite counters.

The five-second progress deadline uses a monotonic clock. The five-second total shutdown deadline bounds draining and recovery together. Unexpected exit while unacknowledged records remain is now explicitly reported as shutdown uncertainty. Readiness alone does not report recovered capture; the first exact durable acknowledgement after a restart does. Retry scheduling, start, exhaustion, recovered capture and unconfirmed termination have distinct finite outcomes. No game engine restart, automatic database deletion, host change or policy activation is introduced.

The publisher also preflights the entire encoded record against the writer's record limit. An input whose body fits but whose encoded envelope is too large becomes an individual capture gap. It no longer poisons the writer and prevents subsequent valid records from being recorded.

Verification includes exact-byte retry, mixed old/new queued records, stale worker messages, the two-replacement limit, permanent versus transient errors, termination refusal/hang, invalid factories, recovery during shutdown, deadline cancellation, adjusted wall clocks and oversized-envelope isolation. Native tests used the real compiled publisher and disk worker twice: once terminating the actual writer after its committed acknowledgement was deliberately lost, and once holding a real SQLite write lock. Both recovered with one replacement, one producer identity, zero duplicate events and at most one live writer. The lost-acknowledgement case replayed the original exact record bytes before accepting a later new record.

This recovery survives a private writer failure while its owning publisher remains alive. The admitted queue is still volatile across loss of the publisher process or host; this is not complete crash capture. Export/retention ownership, complete daily source population, fallback/discard lineage, automatic cross-host review, full runtime pins/replay, causal learning controls and qualified native deployment remain open. Host journal configuration remains unset. Local Node22.23.2/macOS arm64 results do not establish Linux/mount/load/power-loss qualification, natural operation, GTO correctness or publication.
