# tests/a-money-trigger-declares-itself.law.test.ts

A Money Trigger Declares Itself: A Migration That Creates A Trigger On One Of The Nine Money Tables Is Refused Unless It Records That Trigger In `ca_declared_money_triggers` In The Same Migration, Because A Declaration Promised For Later Is What Left Seventy Six Of Them Undeclared And The Critical Alarm Permanently On.

An immutable already-installed record may use independently reviewed historical recovery only when trusted default-branch verification proves its exact current history, trigger/function identities, and an already-applied exact declaration with matching registry rows. New, modified or unapplied migrations still require the same-file declaration. A promised later migration, local receipt, comment or hash allowlist is not proof.

A trigger whose table is supplied at run time is held to the same rule (2026-10-10). `EXECUTE format('CREATE TRIGGER ... ON public.%I', t)` inside `FOREACH t IN ARRAY ARRAY[...] LOOP`, or a target built with `||`, lands on every money table the enclosing loop walks (or its array variable, or the statement's own arguments outside a loop), and each needs its declaration. A definition being compared in a proof block (`pg_get_triggerdef(oid) = 'CREATE TRIGGER ...'`) creates nothing and is not read as one. Migration 20261005183028 put `poker_arena_no_chip_rake` on `club_wallets` through exactly that loop; the gate read `ON public.%I` as a table named `public`, and the critical alarm fired for five days.
