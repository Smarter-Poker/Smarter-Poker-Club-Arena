# tests/a-null-table-hand-is-not-immune-to-retention.law.test.ts

`public.sp_prune_hand_history`'s candidate set required an `EXISTS` match against `public.tables` on `tb.id = hh.table_id`, and NULL never equals NULL, so a `has_human = false` row with `table_id IS NULL` (the `tests/e2e/production-daily-missions.spec.ts` certification fixture, when its cleanup does not run) was excluded from every run of the retention sweep, at any age, forever. The fix admits a row with both `table_id` and `tournament_id` NULL as a candidate on its own, ahead of the original `tables` EXISTS check, which must otherwise survive unchanged for every row that does reference a table; the two F06 guards (`f06_hand_cards_unresolved`, `f06_movement_boundary_retained`) and the `hand_history_retention_policy.horse_retention_days` window must still apply, `has_human IS DISTINCT FROM true` must still be the only rows ever eligible, and the fixing migration must never delete a hand_history row by a literal id list - only the sweep's own computed batch.
