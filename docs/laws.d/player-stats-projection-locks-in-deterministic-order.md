# tests/player-stats-projection-locks-in-deterministic-order.law.test.ts

`fn_project_hand_side_effects_after_post_commit_20260908`'s Projection 2 (legacy `player_stats` fold/winnings totals) inserted one row per seated player of a hand in a single multi-row `INSERT ... ON CONFLICT` with no `ORDER BY`, so Postgres locked the rows in whatever order its join plan produced - not stable across executions. `fn_process_cash_accounting_source` (reached from `fn_credit_agent_commissions_batch`) locks the same `player_stats` rows one at a time in a fixed `ORDER BY club_id, player_id` (`public.apply_rakeback_player_stats`), and the two paths run concurrently for the same hand's players, which deadlocked live on 2026-09-28 (`DatabaseDeadlocksElevated`, board #5070). The fix adds `ORDER BY s.uid::uuid` to Projection 2's source SELECT, matching the cash path's lock order (`v_club` is constant within the statement, so ordering by `uid` alone equals ordering by `(club_id, player_id)` for the overlapping club) - a lock-ordering change only, never a change to which rows are written or their accumulated values.
