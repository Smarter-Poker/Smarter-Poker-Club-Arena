# tests/a-voided-cash-submission-never-moves-a-chip.law.test.ts

`fn_ca_void_unsettled_cash_submission` (migration 20260926231546) exists to unstick a cash table whose oldest unresolved `hand_submissions` row can never be legitimately replayed (a captured seat no longer matches the live table). This law pins that voiding such a row is safe by construction: the function body contains no write to `chip_ledger`, `chip_transactions`, a wallet, or a stack column; it refuses outright when a `hand_atomic_commits` row already exists for the hand (never voids a settled hand); it is `service_role`-only, cash-table-only, and receipt-idempotent; it takes the same advisory lock `fn_ca_resume_hand_submission` takes before it would ever commit, so the two can never race; and `fn_ca_resume_hand_submission`'s candidate query is wired with a `NOT EXISTS` clause against `hand_submission_voids` so a void actually stops the crash-loop re-selection instead of being inert. The paired detector, `fn_ca_stuck_cash_hand_submission_check`, is pinned to contain no INSERT/UPDATE/DELETE of its own - it only ever calls `fn_ca_raise_drift_incident`.
