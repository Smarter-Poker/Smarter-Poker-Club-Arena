# tests/what-a-monitor-reads-is-what-the-repo-says.law.test.ts

What a monitor reads is what this repo says (Realtime Phase 7, 2026-09-06): phase 1 recorded, as its biggest single finding and not one of its own deliverables, that the alert rules running on engine-01 were not the alert rules in this repo IN BOTH DIRECTIONS - measured on 2026-09-06 that was 72 alerts running, 79 declared, 15 declared and never loaded (among them `EngineRefusingSessions` and `EngineCannotReachAuth`, the two this programme wrote in phase 1 precisely so the outage it exists to prevent would page somebody) and 8 running that this repo had never seen. The drift was not carelessness: THREE lists of files had to agree and nothing checked that they did - `prometheus.yml`'s `rule_files`, `docker-compose.yml`'s mounts, and `deploy.sh`'s symlink loop, which named four of the seven, so four rule files existed on the box only because a human hand had put them there and no deploy could ever update them. This law pins that the three lists agree, that no alert group is an empty heading (this repo carried three - `cron-health`, `postgres-health` and `vercel-health` - promising coverage they did not contain while the box held the rules, and a deploy would have deleted the box's copies), and that the `MonitoringCanary` exists, is unconditional (`vector(1)`, so it cannot be quiet for a legitimate reason), is severity `canary` so it wakes nobody, and is actually looked for by `scripts/ci/check-alert-rules-match.mjs` - because every other rule is silent when things are well, which makes "no alerts" and "no monitoring" the same observation, and they were the same observation for twenty-two hours.
