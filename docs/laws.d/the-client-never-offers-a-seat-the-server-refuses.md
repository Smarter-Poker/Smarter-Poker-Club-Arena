# tests/the-client-never-offers-a-seat-the-server-refuses.law.test.ts

The multi-table cap is stated twice by necessity: the server decides it, and the client has to know it in order to stop short of it. `MultiTablePage` has always said so plainly, and said which direction the duplication may fail in: "this is the client refusing to offer a seat it knows the server would decline, and never the other way round."

The reasoning was right and the number went stale. The cap was raised to six on 2026-08-21 and lowered back to four on 2026-09-02; the client kept six on any screen 1024px or wider. For ten days every desktop opened tabs five and six and had the buy-in refused at the door, which is exactly the direction the note forbids. Two comments in the same file disagreed about the same number.

This law derives the server's answer from the migrations rather than retyping it, and holds the client to it. The cap is global and asset-neutral: a Diamond seat and a chip seat take the same slot, in the chip buy-in body, in the Diamond buy-in door and in the `table_seats` trigger. The arena is what made a second server-side copy of the number exist, which is why the law lives with the Diamond work.
