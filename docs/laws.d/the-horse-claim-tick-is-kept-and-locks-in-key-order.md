# tests/the-horse-claim-tick-is-kept-and-locks-in-key-order.law.test.ts

`ca-horse-claim-due-minute` runs every minute, 1,440 times a day, the same cadence as `ca-auto-reconcile-tick`, which was retired on 2026-09-24 for repairing nothing. This job was audited against the same standard on the same day and KEPT, and this law records that decision so the next agent does not re-derive it and cannot quietly reverse it.

It is kept because it repairs no state and stands in for no writer. It IS the horse's claim button: a human is shown a completed reward and presses Claim, a horse has no browser, so the engine presses for it, which is the input-device branch CLAUDE.md 10.5 names as legitimate alongside HorseLogic, `scheduleHorseAction` and the synthetic heartbeat. Nothing else claims for a horse, so unscheduling it would leave horses unpaid, the exact opposite of what retiring a compensation loop achieves.

The honest counter-argument is recorded rather than buried. Measured on production 2026-09-24: of 54,661 claims since 2026-09-09, 54,141 (99.05%) were paid on the first tick after completion and none was paid more than a day later; it never approached its limit of 500, its busiest minute in 14 days being 294. The clock never adds a row to its candidate set, since `completed_at >= now() - interval '7 days'` is a lower bound and time only ever removes, so rows enter only when a writer sets `completed`. It therefore does behave like a poll standing in for a trigger. What makes it legitimate anyway is that the state it acts on is not a defect: completed and unclaimed is the normal, correct state of a reward for every player, and a human sits in it for up to seven days by choice. Paying it is an action in the domain, not a correction of a bad write.

What was genuinely wrong was its lock order. 33 claims died with `deadlock detected` between 2026-09-09 01:12 and 2026-09-22 13:17 across 29 horses, filed as `CH3:horse_claim_failed`. The whole loop is one transaction, so it holds every row lock it takes for the length of the batch, and it took them in `completed_at` order while the four `daily-missions-outbox-minute` shards update one player's rows in a single unordered bulk UPDATE on the same minute. Overlapping rows taken in two different orders is the cycle. `fn_expire_daily_challenge_rewards` hit the same failure on 2026-09-09 and its body carries the answer: primary key order gives every caller the same acquisition order, and `SKIP LOCKED` leaves a row another writer holds for the next run. `20260924183308_the_horse_claim_takes_its_rows_in_primary_key_order` gives the claim loop both. No money was lost to the deadlocks: all 1,982 rewards belonging to those 29 horses were claimed on a later tick and none expired unclaimed.

The law pins that no migration unschedules the job, that the roster still lists it, that the fixing migration schedules and unschedules nothing and drops no function, and that the shipped function still chooses candidates oldest first while locking in primary key order with `SKIP LOCKED`. The negative that matters, that the locking select is not ordered by `completed_at`, is asserted against source with comments stripped, because the migration's own header quotes the broken ordering in prose (CLAUDE.md 7.3). The detector is self-tested against the defective shape it exists to catch.

Retiring this job is a deliberate edit to this law with an argument attached, not a quiet line in an unrelated migration.
