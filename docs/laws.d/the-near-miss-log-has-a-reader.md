# tests/the-near-miss-log-has-a-reader.law.test.ts

`bbj_near_misses` was built to say whether a jackpot that has not paid is
strict rules working or something refusing hands, and for four days it had
three writers and no reader at all - the exact failure its own table comment
cites CLAUDE.md 10.86 rule 3 for. This keeps the reader attached: a scoped,
authorised `fn_bbj_near_miss_summary` in a migration, a panel that calls it,
a label for every gate the engine can name (read from `RakeConfig.ts`, never
from the creating migration's prose, which names five gates no writer emits),
`mini_refused` classified before `mini_` on both sides so a hand that
qualified and was turned away is never filed as one that never qualified, and
"the log could not be read" kept distinct from "nothing was refused".
