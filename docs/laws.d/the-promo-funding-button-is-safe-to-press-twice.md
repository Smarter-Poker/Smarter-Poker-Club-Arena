# tests/the-promo-funding-button-is-safe-to-press-twice.law.test.ts

fn_diamond_game_fund_promo, which moves a host's chips into the promo wallet that pays every Diamond Games prize, takes its idempotency key from the CALLER and the keyless two-argument door is dropped rather than left open beside it: the server namespaces what it is given ('diamond-games-fund:' || p_key) and refuses a key of the wrong shape instead of falling back on one it mints itself, which is the defect this law exists to prevent (a probe on production proved two identical presses of 25 chips moved 50 and wrote two journal legs); the replay guard reads chip_ledger only after fn_diamond_game_cover_lock has taken the host's wallet row FOR UPDATE, which is what makes check-then-act safe, and answers a second press with the balances and replayed = true rather than an error; the guard is load-bearing, so the function refuses to return unless a leg actually carries the key; both host shapes now write the operator's own wallet history and amounts finer than a cent are refused in words; and the browser half is pinned too, because one key per PRESS would restore the bug exactly: both operations pages mint one key per intent, hold it across a thrown request, and clear it only where the server has answered.
