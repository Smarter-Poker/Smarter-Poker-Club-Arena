# Operation maintenance database authority

This additive support remains inactive until a verifier records the exact six-component policy compatibility receipt and the sole installed release controller activates it. The current hourly maintenance and v3 thaw remain unchanged before activation. The policy digest is `1fed78c7afc00a220839dd198f2a362befe0fbe9655b2574d9d037d2864b2bda`.

Expansion prerequisites are the prepared release journal `20260911151748_private_global_release_journal.sql`, provider boundary `20260911160341_provider_operation_boundary.sql` (SHA256 `487edd561b2936d84d0dc31a19eab67d373d6bfcb30489b3471b195424ef9773`), and the exact installed v3/clock catalogs pinned in the migration. Missing or drifted prerequisites refuse the entire transaction. The native fixture supplies those exact dependencies; source preparation is not their production installation.

The database clock begins at operation admission, including last-hand drain. The normal target is 300 seconds, the forward deadline 1,200 seconds, and the absolute deadline 1,800 seconds. No deadline authorizes reopening. Engine ownership adoption is independent of the controller's session lock and epoch.

Before this change, the installed five-argument v3 thaw already records the full database-observed duration, snapshots exact clock targets, credits installments, and releases only after every target reaches a future release boundary. The old checkpointed worker's 900-second input guard does not limit the authoritative ledger duration. This change retains that implementation behind a pinned private wrapper and adds operation authorization and wave-specific suffix receipts. It does not lengthen legacy caps.

Only a verifier-proven engine replacement may admit platform scope. Table-scoped maintenance is rejected. Existing service engine writes can resume in authorized waves while browser admission remains globally held until full acknowledgment. Event tables must share a wave so one event's clock cannot resume before another table in that event. Arbitrary partial maintenance requires a separate inventory and qualification of every writer.

The runtime must provide real parked/between-hands proof, follow the credited-through boundary before resuming each exact wave, and acknowledge actual resumption. Authorization committed without an acknowledgment is an unknown physical outcome after adoption or expiration. The database preserves that receipt and enters recovery-required; it cannot infer whether the process resumed and must not blindly add credit. A committed acknowledgment survives response loss and restart.

The notification singleton is a sanitized wakeup. Durable operation reads, including all immutable wave receipts, remain authoritative. Browser reads expose policy and activation identity even when idle, preserve an unresolved known interval, and return the known completed interval's release identity before a later interval.

Preparation limits: no production activation or provider proof is created by the migration or native fixtures. Independent installation and compatibility evidence is still required. Native tests use a socket-only PostgreSQL 17 fixture and never accept a production connection string.

The partial-wave gameplay rehearsal uses the current twelve-argument accepted-hand authority, its private lease/stack/history cores, and the actual seat freeze trigger. With the first tournament wave acknowledged, the later cash wave and global ancillary freeze remain held. A fresh hand moves two exact seat generations from 10/10 to 11/9, synchronizes their tournament roster balances, and writes one hand history, atomic commitment, and projection outbox entry. The same request then replays without another write. A wrong lease generation is refused; neither the private stack core nor the accepted-hand door becomes a client RPC.

The service-role JWT is the existing engine's write authority. The rehearsal never enables the generic freeze bypass for the accepted hand. It does not claim that the database infers physical dealing from an acknowledgment, nor that a held engine may start another hand: the runtime owns the actual pause/resume boundary. The fixture uses explicit local administrative setup to prepare its synthetic seats and historical hold, then executes the real service RPC with the relevant triggers enabled.

`tests/maintenance/native.py` accepts the sealed E2 archive and a provider migration path, snapshots the maintenance/provider SQL, and records input fingerprints. `--integration-script` lets another owned composition use the same isolated database; that script receives `cluster.json` and an evidence directory, and must emit `cases.json`. ## Final global credit and certified release

After every physical wave has its durable acknowledgment, `fn_ack_engine_maintenance_resumed` advances a private global checkpoint. The endpoint stays fixed across the existing four-second, 200-row (40 tournament-level row) worker installments. Partial progress is a held operation with `global_tail.status = pending`; it is not an uncertain physical resume and must not replay any wave. A checkpoint that overruns finishes its original endpoint before another checkpoint may be appended. There are at most eight checkpoints, and none extends the original continuous hold deadline. A previously authorized recovery after the deadline remains a separate explicit authority.

The final immutable certificate binds interval, engine token and generation, the existing safe-resume receipt, every ordered wave acknowledgment, all captured target identities and credited amounts, and per-clock-class counts. Table gameplay and event level clocks remain fixed at their actual wave acknowledgment. Add-on purchase opportunity (`addon_period_ends_at`) remains globally scoped because buying is held through the global purchasing release. Its original remaining opportunity survives that full tail; this does not shift the minutes-based late-registration `started_at` anchor. Only the globally held target tail advances to the final endpoint. No certificate may be minted at or after its endpoint.

The sanitized `engine_maintenance_global_releases` table exposes only interval, receipt, generation, certified endpoint and certification time. Both database global freeze predicates evaluate this exact receipt synchronously. A target or deadline without this receipt never opens admission. The browser projection returns `global_release_receipt` and `global_release_at` separately from the normal target, and returns the final receipt as the release identity once its boundary is reached. The later operation-row `resumed` update is durable readback bookkeeping, not the release authority.

The runtime's informed shared freeze predicate uses its database-anchored monotonic clock to observe the certified boundary directly; a delayed timer is unnecessary. That first true-to-false observation delivers the same one-shot, cancelable thaw listeners as the legacy explicit transition. A later callback cannot deliver those listeners twice.

A process that never receives a committed certificate must remain locally fail-closed until durable readback. The database-authoritative hold still ends at the certificate's endpoint; a disconnected process may delay ancillary jobs after that release, but cannot extend the interval or add maintenance clock credit. Simultaneous client/process release during a network partition is not claimed. Reconnect and cold restart read the original certificate without repeating physical waves or clock writes.

The certificate transaction also has deferred private/public constraint checks that reject an endpoint reached during aggregate, lock, trigger, or final-insert work. The native test delays a receipt insert beyond the endpoint and proves that the certificate, public release projection, and all uncommitted suffix changes roll back together. This is the last SQL-level check before commit. PostgreSQL can still stall afterward during scheduling or WAL commit/visibility; SQL source alone does not prove an absolute future-commit bound. This residual commit-boundary limitation is an activation review prerequisite, not a claimed network/storage liveness guarantee.

A wave ACK whose exact captured timestamp is still ahead of the database receives a distinct pre-write refusal. The real store may retry that same immutable ACK up to four calls separated by five milliseconds. It neither changes the timestamp nor repeats physical resumption. An unknown response, lower-bound violation, stale owner or malformed proof does not use this retry path.

The add-on scope correction explicitly supersedes SQL SHA256 `82dd06afd275038baa014f0e8d3ad16f8bd4e71822f8a7419ebcb12bd39c6b31`, whose complete 17 + 13 matrix is preserved separately. The receipt schema is unchanged; new certificates bind the actual revised target scope and credit. A separate real Runtime/SQL regression proves that an early event wave with a one-second add-on opportunity survives a longer global tail, while level credit stays at its wave ACK and exact replay adds nothing.
