# Exact-run Daily Missions fixture cleanup

The Daily Missions worker previously kept its extra account and synthetic hand only in memory. A worker timeout could leave both behind while the outer workflow cleaned only its primary account. The repaired path persists account and hand intents before Auth creation, persists hand-start and hand-created markers around the insert, and invokes cleanup from the workflow outside browser workers.

Every record is bound to the exact run and attempt, reserved email and predetermined account UUID. The hand ID derives from that account UUID. Files and their directory entries are synced before mutation. No password, session or service key is written into this ownership ledger. The always-run artifact step preserves these records and successful or partial cleanup observations. Local certification requires `E2E_FIXTURE_RUN_ID` and `E2E_FIXTURE_DIRECTORY` when the GitHub run identity and runner temporary directory are absent.

Cleanup reads only the current run/attempt directory. It verifies the live Auth UUID and reserved email, then checks the hand's exact ID, null table/tournament, `has_human=false`, empty players/actions and single matching mission-event owner. Its conditional DELETE repeats those predicates and requires an empty readback before the account can be removed by the existing guarded RPC. It then verifies Auth absence and the existing dependent-resource closure. One account's failure does not authorize deleting that account, nor stop cleanup of separately owned accounts; any failure leaves the overall cleanup incomplete. Automatic age-based sweeps were removed from post-deploy provisioning and the commerce suite; their exported legacy utilities are not invoked by these paths.

A started insert with no acknowledgement and no visible row is unresolved, not successful cleanup. An exact visible committed row can be reconciled, removed and recorded durably. A deleted hand is recorded before deleting its owner so later cleanup is idempotent. The controlled certificate cleanup also reads the deterministic hand and includes that absence in its evidence digest. Early original-run failure before the missions worker starts still relies on the journal's independent account-creation outcome gate. Later host-loss/recovery cannot use a new empty filesystem to invent original hand-write outcomes: missing original records and absent ambiguous rows block completion. This change provides worker-timeout recovery, not a new remote journal protocol or automatic artifact-import recovery.

## Notification coverage

The production browser no longer invokes `enqueue_daily_mission_reset_notifications(date, 5000)`. It inserts a deterministic notification for the exact marked fixture account through existing service table authorization, verifies notification-to-push delivery and exercises the preference UI. Replaying the same fixture notification uses its primary key; this does **not** certify global enqueue selection or scheduler execution.

A separate isolated PostgreSQL test loads the real enqueue function body, grants and deduplication index from the reviewed migrations. It tests preference selection, replay deduplication, bad limits and denied authenticated execution, with a synthetic caller-identity function. It does not certify the production caller-identity implementation or cron installation. No production RPC body, grants, or schema was changed.

## Validation boundary

The regression suite kills a real child worker after durable intent creation, then verifies exact cleanup through simulated HTTP responses. It also covers another run/attempt, real-user marker mismatch, foreign/human hands, unresolved creation, lost hand response reconciliation, conditional deletion readback, and fixture-only notifications. The PostgreSQL test executes the actual enqueue SQL in a disposable native database. Related unit tests and test discovery/lint validate integration. None of these results claims a new production browser certificate or executed production cleanup.
