# Horse commitment audit PostgreSQL regression

The existing `accounting_postgres` job invokes `scripts/ci/test-horse-commitment-audit.py` directly. Script or fixture changes select the parent job and existing routing tests; migration changes already select accounting. This adds no workflow, scheduled task or production connection. Required final-revision CI remains the execution evidence.

The runner retains seven sequential fresh PostgreSQL17 clusters/databases, one live cluster at a time:

1. The original R1 function must fail the mixed-case duplicate roster assertion with exact `P0001: roster_review_count: mixed_case_duplicate`. Unexpected success or another failure refuses the run. This fail-fast control does not claim all24 cases ran.
2. The actual forward migration `20260917051350_horse_commitment_reviews_preserve_format_and_canonical_rosters.sql` must pass the85 format/commitment cases.
3. The same forward migration must pass the24 roster cases.
4. The actual private reader migration `20260917052511_horse_private_commitment_review_reader.sql` must pass the separate27 synthetic-row payload, tuple-pagination and role-refusal fixture. Reinstalling that migration must fail with exact `P0001: horse_daily_reader_already_exists`, preserving its function definition, owner, ACL, the three tables' owner/RLS/table-and-column ACL metadata, and diagnostic rows. The fixture's final rollback must leave that same snapshot unchanged.

These are109 candidate case rows. Job 5's 58 checks are separate from both. Separate migration controls alter the original function's cost or body in the disposable database, require the exact preimage refusal and unchanged drifted state, then restore only its captured fixture definition. Applying the forward migration twice must preserve the function metadata and diagnostic tables. These controls do not increase the109-row count.

The reader's27 rows are separate from those109 cases. `reader-page.sql` is the byte-exact retained fixture, including its own BEGIN/ROLLBACK and every original assertion; the wrapper appends only a completion SELECT after the final rollback. Its post-fixture comparison uses a fresh psql session, including when a fixture assertion fails. Every invocation uses a new process/connection, so the fixture cannot nest over a caller transaction or inherit another caller's role. A command timeout remains failure; existing cluster cleanup still runs.

`reader-auth.sql` uses the exact `auth.role()` body from the owner's September17 readback, MD5 `f31486fed08a7402e89d4aa71b0ad273`. It preserves the intentional trailing space after SELECT; the historical excerpt omitted that one byte and has a different digest. It creates a disposable auth schema with explicit fixture grants and exercises synthetic request GUCs. Those grants and GUCs do not prove production JWT authentication, the actual pre-request hook, gateway/schema-cache routing, or the provider's complete effective ACL. The migration guard checks all three private tables' API-role table/column privileges; the retained behavioral fixture checks reader service admission, anon/authenticated refusal and direct review-table SELECT refusal. It does not replace the broader effective-ACL, realistic-data/plan/latency, outer deadline or transport-retirement qualification. Source population and whole-day completeness remain unknown.

The setup deliberately models only four source tables. The historical `20260914161209_horse_committed_pot_daily_audit.sql` supplies the diagnostic tables in each empty fixture database; this is not permission to reapply it to production, where its recorded version is20260914161209. The original function and corrected85/24 SQL inputs preserve every frozen assertion. The only fixture syntax repairs are the roster CASE-expression parentheses and disambiguated `stored_review` aliases. No fake digest or validator is installed: the existing provider must supply PostgreSQL17 and pgcrypto. Fixture roles have no login; the SQL exercises the actual service-role function permissions.

The wrapper requires explicit absolute provider/source/allocation/output paths, refuses a preexisting output, verifies input hashes and records binary hashes. It constructs a credential-free environment, private HOME and local Unix socket with TCP disabled; no ambient PG settings, credential files, connection URLs or package installation are used. Sources are loaded once and passed unchanged to psql. Changed production migration bytes require updating the source pin and qualifying those exact bytes.

Work is bounded to180seconds with at most45seconds of cleanup. Command/server logs are retained separately from results, including the first failure and cleanup failure. The complete result and bounded output tails from failed commands are also emitted into the existing CI job log, so workspace removal cannot hide the original diagnostic; no additional cloud artifact storage is introduced. A single fast stop must be followed by stopped status, absent PID and empty socket before an allocation is deleted. Unconfirmed cleanup remains failure and retains the allocation. SIGKILL or host failure requires the existing runner owner to retire that exact allocation; this wrapper cannot independently certify its own host. The provider retains responsibility for CPU/RAM/disk admission (oneCPU,512MiB,1GiB requested), the host free-space floor and evidence retention. No automatic retry occurs.

This is diagnostic-function qualification against synthetic rows, not full financial/schema qualification, installed-state proof, historical Horse census, GTO or learning activation. No live credentials, rows or installation are part of this gate.
