## Finite coverage

| Spec | Held transaction and competing operation | Required committed result |
| --- | --- | --- |
| `creation-commit.spec` | A creates a feeder; B ensures the same target under another name; A commits. | One feeder; B returns `existing_active` with A's exact ID. |
| `creation-rollback.spec` | Same race; A rolls back. | One feeder created by B; A's row and observation do not survive. |
| `edit-after-creation.spec` | A creates a feeder; B changes the target to a PKO label with false flags; A commits. | B gets the exact live-target refusal; target stays plain. |

| `restart-rollback.spec` | Same restart race; A rolls back. | One child created by B, pointing to the immediate source and original target. |

Each file contains exactly one explicit permutation. Actor setup commits each connection's actual backend PID before either transaction begins. The contender step is unannotated; the following observer must find the registered owner's PID in `pg_blocking_pids` for the registered contender, with both connections in this database and carrying the expected application names. No arbitrary sleeps, manufactured wait markers or polling repair loops are used. PostgreSQL documents that [`pg_blocking_pids`](https://www.postgresql.org/docs/current/functions-info.html) identifies sessions blocking a lock request.

Final assertions independently check outcome labels, committed IDs, cardinality, NULL field capacity, minimum/table sizes, source/target identity, target labels and absent game/funding effects. ## Required acceptance behavior

The asset manifest is `catalog-candidate.json`. The existing CI job now selects the direct caller in source, and its change classifier includes the caller, captured fixture, probes, result consumer and operations regressions. The manifest also binds all three native probes and the ticket wrapper's included SQL. The fixture/driver/consumer independently received bounded source review; their pure regression checks passed. Actual CI invocation and native acceptance must pass before calling the database checks enforced.

**A zero process exit is insufficient.** Stock `isolationtester` prints SQL errors and can continue after teardown errors. The qualified consumer must reject any unexpected SQL error/fatal result, assertion failure, timeout, cancellation, deadlock, transport failure, setup/teardown failure, unfinished step or missing case output, regardless of process exit. It must also require the actual `observed_wait` step and the matching final assertion marker. These conditions follow the [PostgreSQL test-runner source](https://doxygen.postgresql.org/isolationtester_8c_source.html), and must be verified against the exact admitted binary.

All expected business refusals are caught narrowly inside fixture helpers. An uncaught SQL error is therefore never an accepted result for these six cases. The observer must actually execute its blocking query; its name in a transcript is not evidence that the assertion passed. Require final source-bound results and independent review, plus fixture-disposal evidence. Inject a missing assertion and an unexpected SQL error during consumer qualification to demonstrate rejection; do not change the application's guards to obtain a pass.

Each actor has a final rollback in session teardown to release an unfinished transaction on a failed run. After a successful explicit commit/rollback, PostgreSQL emits the known `there is no transaction in progress` warning there. A qualified output consumer may accept only that exact warning in those two teardown positions; never turn this into a general warning or error allowlist. The [PostgreSQL parser grammar](https://coverage.postgresql.org/src/test/isolation/specparse.c.gcov.html) places optional teardown after the session's steps. Pin and verify grammar and output behavior against the admitted provider version; the linked generated source is not a qualified binary.
